```bash
for f in $(find apps/server/src -name '*.entity.ts'); do
```

### 1.2 심사② — 대부분 해결 🟢

중간결과물이 화면에 단계별로 보입니다.

| 단계 | 어디서 보이나 |
|---|---|
| 수집 | 문서함 — 출처(메일 수집 / 직접 업로드), 발신자 |
| 변환 | `convertedFilePath`(HWP·이미지→PDF), `markdownPath` |
| 추출 | 문서함 → 검토 — 추출 JSON을 열어 보고 고칠 수 있음 |
| **규칙판정** | 검증 패널 — **규칙별 판정 + 근거 문장 + 「근거 보기」** |
| **실무자 확인** | **「다음에 하실 일」** — 무엇을/어디서/고치면 어떻게 되는지 |

9월에 없던 것 중 추가된 것: **규칙별 근거 표시**와 **할일 안내**입니다.
특히 할일 안내는 "중간결과물을 보여주는" 수준을 넘어 **다음 행동까지 지정**합니다.

> 남은 부분: 한 문서에 대해 수집→변환→추출→판정→확인을 **한 화면 타임라인**으로
> 보여주는 뷰는 없습니다. 각 단계가 서로 다른 화면에 흩어져 있습니다.
> 질문이 나오면 이 점은 인정하는 편이 낫습니다.

### 1.3 심사③ — 구조 구현 + 규칙 4건 등록 🟡

9월에는 `exceptionRule`이 **타입 정의만** 있었습니다. 지금은 다릅니다.

| | 9월 | 지금 |
|---|---|---|
| 엔진 평가 분기 | 없음 | 구현 (2026-11-13) |
| 승인 사유 기록 | 없음 | 구현 — 걸린 규칙을 승인할 때 사유를 남긴다 |
| 「예외 후보」 집계 화면 | 없음 | 구현 — 평가 대응 탭 |
| 원장에 등록된 예외 규칙 | **0건** | **4건** (2026-11-14) |

실측 분포:
```
crossCheck 11  /  calcRule 12  /  riskFlag 5  /  exceptionRule 4   (합 32)
```

등록된 4건:

| id | 상황 | 어떻게 나왔나 |
|---|---|---|
| `R-203-E1` | 전 직장 상실신고 오류로 고용보험 중복가입으로 보이는 경우 | **시스템이 먼저 발견** — R-203 승인 4회가 후보로 집계됨 |
| `R-101-E1` | 사업 중 법인전환으로 사업자등록번호가 달라진 경우 | 담당자 확인으로 실제 경험임이 확인됨 |
| `R-308c-E1` | 계좌 압류로 사업체 명의 계좌에 입금 불가 | 담당자 확인으로 실제 경험임이 확인됨 |
| `R-104-E1` | 사무실 업종 + 공유오피스 의심 주소 → 현장확인(실제 근무 여부·수행 업무) | 담당자가 직접 제시 |

**가장 강한 이야기는 `R-203-E1`입니다.** 담당자가 기억해 내서 적은 게 아니라,
같은 규칙을 **4번 반복해서 넘긴 이력**이 시스템에 먼저 후보로 올라왔습니다.
한 번이면 개별 판단이지만, 반복되면 규칙 후보라는 것 — 암묵지를 기억에만 의존하지 않고
쓰는 과정에서 모으는 구조입니다.

**아직 안 된 것도 같이 밝히세요.**

- 실무자가 화면에서 규칙을 직접 추가·수정하는 **"예외규칙 관리" 메뉴는 없습니다**
  (지금은 담당자가 적어 주고 JSON 원장에 등록하는 방식)
- 네 규칙 모두 **탐지까지만 자동**입니다. 그 뒤(전화 확인·서류 수령·현장확인)는 사람이 합니다 —
  서류에 없는 사실을 확인하는 일이라 그렇습니다. 이 경계를 규칙에 적어 둔 것이 설계 의도입니다
- 예외 상황에서 받는 서류 5종(법인양도양수 계약서·고용승계확인서·현금수령확인서·
  제3자 통장사본·가족관계증명서)이 **서류 종류 목록에 아직 없습니다.** 안내문에 글로만 있고
  필수서류 체크리스트로는 못 씁니다 — 다음 작업입니다
- 예외 규칙은 **기본 규칙의 판정을 바꾸지 않습니다** — 이건 한계가 아니라 설계 원칙입니다(ADR-07)

**`R-104-E1`은 성격이 다릅니다.** 앞의 셋은 "지침대로 하면 걸리는데 실제로는 괜찮은" 경우고,
이건 **지침에 사업장 장소 규정이 아예 없어서** 공식 요건으로는 걸러지지 않는 경우입니다.
사무실 업종인데 주소가 공유오피스로 의심되면 현장확인을 나가야 한다는 것 — 지침에 없고
담당자 경험에만 있는 판단입니다. **"지침의 공백"** 유형으로 따로 말씀하시면 심사③ 답변이 두 겹이 됩니다.

**발표 문구 예시**

> 지적③은 구조를 만들고 규칙 3건을 등록했습니다. 예외는 지침서에 없고 실무자 경험에만
> 있어서, 코드를 먼저 쓸 수 없는 영역입니다. 그래서 받을 구조를 먼저 만들었습니다.
> 규칙에 걸렸는데 담당자가 승인한 건을 모아 반복 횟수 순으로 보여주는 화면을 두었고,
> 실제로 한 규칙이 4번 반복된 것이 잡혀 첫 예외 규칙이 됐습니다.
> 다만 예외 규칙이 자동으로 통과시키지는 않습니다. 확인 절차를 안내하고 결정은 사람이 합니다.
> 실무자가 화면에서 직접 규칙을 등록하는 기능은 아직 없고, 향후 과제입니다.

**시연 순서** (질문이 나오면)

```
평가 대응 탭  →  「예외 후보」 표  →  R-203 승인 4회 / 승인 사유
              →  근로자 검증 화면  →  R-203 에 "예외 후보: R-203-E1" 배지
              →  R-203-E1 행의 확인 절차 안내 (근로자 전화 → 전 직장 정정 → 재수령)
```

### 1.4 심사④ — 미착수 🔴

실무자 테스트 배포본이 없어 후기를 받지 못했습니다. 막는 요소:

- 프로덕션 패키징 미완 (Electron 안에서 NestJS 동봉 구동)
- `synchronize`가 production에서 꺼지는데 **마이그레이션이 없음** → 배포본 스키마 생성 실패 위험
- 테스트 관리자 계정 잔존 (단, `check-release.mjs`가 배포 빌드를 **중단**시킵니다)

**대안으로 제시할 것:** "기관 내부 서버 1대 + 브라우저 접속" 방식이면 Electron 패키징
없이도 테스트할 수 있습니다. 실제로 이번 개발 내내 `npm run dev:web`(브라우저 모드)로
작업했고 정상 동작합니다.

| **A. 정직하게 한계로** | "정량 평가는 표본 부족으로 수행하지 못했다"고 명시하고 측정 설계만 제시 | 0 | 중 — 솔직함은 감점이 아님 |
| **B. 합성 서류로 추출 정확도 측정** | 17종 생성 → 정답지와 항목별 대조 → 정확도 표 | 노트북 + 반나절 | 상 |
| **C. 규칙별 AI-사람 일치율** | 판정이력 집계 | 표본이 늘어야 의미 있음 | 현재는 낮음 |

**권고: 출장 후 B를 하고, 그 전까지는 A로 써두세요.**
B는 노트북이 필요하고(합성 서류 생성에 Electron, 추출에 API 키), 돌아오신 뒤 제가
`npm run ai:score`를 만들어 돌리면 반나절이면 표가 나옵니다.

A로 쓸 때의 문구 예시:

> 본 연구는 시스템 설계와 구현에 중점을 두었으며, 정량적 성능 평가는 확보한 실제 표본이
> 1개 기업·1명 참여자로 제한되어 통계적 유의성을 갖추지 못했다. 다만 평가를 위한 측정
> 장치는 구현되어 있다. 판정이력 테이블에 AI 자동판정과 담당자 승인이 쌍으로 기록되므로,
> 표본이 축적되면 규칙별 인간-기계 일치율을 산출할 수 있다. 이를 향후 과제로 남긴다.

## 5. 예상 질문과 답변

실제로 나올 법한 것만 골랐습니다. **모르면 모른다고 하는 편이 낫습니다.**

**Q. AI가 틀리면 어떻게 됩니까?**
> AI는 판정하지 않습니다. 값을 읽는 역할만 하고, 대조와 판정은 규칙엔진이 합니다.
> AI가 값을 잘못 읽으면 규칙 대조에서 불일치로 걸려 담당자에게 넘어갑니다.
> 실제로 성명 오타 하나가 세 규칙(R-201·202·209)에서 동시에 검출되는 것을 확인했습니다.

**Q. 모델을 바꾸면 시스템을 다시 만들어야 하나요?**
> 아닙니다. 규칙 판정과 할일 안내는 모델과 무관한 결정적 코드입니다.
> 모델 교체는 추출 정확도에만 영향을 줍니다. 이 분리가 설계의 핵심입니다.

**Q. 개인정보는 어떻게 보호합니까?**
> 주민등록번호는 외부 AI 전송 전과 DB 저장 전 두 지점에서 마스킹합니다.
> 생년월일 6자리만 남기는데, 이는 만 연령 산출(R-200)에 필요하기 때문입니다.
> 시스템은 기관 내부 1대에서 동작하고 실자료는 기관 밖으로 나가지 않습니다.
> (※ 스캔 이미지 자체는 AI에 전송되므로 마스킹 한계가 있음 — 질문받으면 인정할 것)

**Q. 규칙 4유형이라면서 왜 3개만 구현했습니까? (심사③)**
> §1.3 문구 사용.

**Q. 실무자가 써봤습니까? (심사④)**
> 아직 못 했습니다. §1.4의 대안(내부 서버 + 브라우저 방식) 제시.

**Q. 평가는 어떻게 했습니까?**
> §4의 A 문구 사용. 변명하지 말고 측정 설계를 보여줄 것.

**Q. 지침이 바뀌면요?**
> 규칙이 JSON 원장에 있어 파일만 교체하면 됩니다. 다만 지침 개정을 사람이 읽고
> 원장에 옮기는 작업은 수동입니다. 이것도 한계로 적어두었습니다.
