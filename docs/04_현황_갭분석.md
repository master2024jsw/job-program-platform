## 2. 요구사항별 상세

### REQ1. 비정형 서류 자동 수집·구조화 — 🟢

- 구현: `modules/mail-collector/` (IMAP, 발신자 메일로 기업·근로자 자동매칭), `modules/documents/converters/` (HWP·이미지→PDF), `documents/gemini.service.ts` (JSON 추출 + `missingItems`)
- 부족:
  - Gemini 프롬프트가 범용이다("문서 종류를 스스로 판단"). **서류 종류별 추출 스키마**가 없어 검증엔진 입력으로 쓰기 어렵다.
  - `Document` 엔티티에 `businessId`가 없다.

### REQ2·REQ3. 도메인 검증엔진 — 🔴 (논문 핵심, 최대 공백)

- 현재: `common/domain-validation-engine.interface.ts`, `common/judgment-history.repository.interface.ts` 타입 선언만 있음. 호출하는 곳 없음.
- 관련 부분 구현: `modules/subsidy/` 에 지원금 신청 가능일 계산(`eligibilityMonths`, 기본 3개월) 있음 → `calcRule`의 일부지만 검증엔진 밖에 있고, 설정이 전역(`id='default'`)이라 사업별로 다르게 둘 수 없음.
- 필요한 것:
  - 규칙 4유형(`crossCheck`, `calcRule`, `exceptionRule`, `riskFlag`)을 **DB/JSON 데이터로 정의** (사업 `typeCode`별, 지침 연도별 버전)
  - 규칙 실행기: 추출 JSON → 규칙 순차 적용 → 결과(통과/위반/위험/보류 + 근거 문구 + 적용 규칙 ID)
  - 판정 이력 테이블 (`JudgmentHistoryRepository` 실제 구현)
  - 1차 대상 규칙: [01 문서 1.2절](01_업무프로세스_자동화매핑.md) 표의 현장실습훈련 항목
- ⚠ **규칙 원장이 저장소에 없음**: 원님이 보유한 실무 규칙 목록을 `docs/05_검증규칙_원장.md`로 옮겨야 엔진을 채울 수 있다.

### REQ4. 실무자 검토·보정 — 🟡

- 구현: `DocumentAnalysisStatus.REVIEWED`, `reviewedData` (실무자 보정값)
- 부족 (논문 4.3절 3원칙 대비):
  - 선별 제시: 위반·저확신 항목 강조 없음
  - 근거 제시: 원본 PDF와 추출값 나란히 보기, 규칙 판정 근거 표시 없음
  - 이력 축적: AI값 → 실무자 수정값 변경 이력 저장 없음

### REQ5. 기관 내부 완결 — 🟡

- 충족: 로컬 SQLite, 외부 통신은 AI API 호출뿐 (논문 Ⅳ장과 일치, Gemini는 PoC용이고 정식 전환 시 ZDR API로 이전한다고 논문에 명시됨)
- ⚠ **서술과 구현 불일치**: `renderer/src/content/guide-content.ts`의 `SECURITY_TEXT`는 "전송 전 개인식별정보 마스킹", "ZDR 정책"을 안내하지만, 서버 코드에 마스킹 로직이 없다. 본발표 시연 전 둘 중 하나로 맞춰야 한다.
  - (a) 전송 전 주민번호·계좌번호·연락처 마스킹 구현
  - (b) 안내 문구를 현재 상태에 맞게 수정

## 3. 심사 지적사항별 상세

### 심사① 로그인 시점부터 사업 구분, 사업별 증빙서류 양식 식별 — 🟡

- 이미 있음 (설명 자료로 활용 가능):
  - `Business`(id: `BIZ-{연도}-{유형코드}`), `UserBusiness`(담당자↔사업 배정), 상단바 사업 선택 드롭다운(`AppShell.tsx`)
  - `SetupPage`: 기관 생성 → 관리자 생성 → 첫 사업 등록 마법사
  - `CompanyBusiness`: 기업 × 사업별 진행상태
- 부족:
  - `Document`, `Worker`, `MailLog`, `SubsidyCalculation`, `SubsidySetting`에 `businessId` 없음 → 사업을 바꿔도 같은 데이터가 보임
  - **사업별 필수 증빙서류 목록** 정의 없음 (예: SENIOR 일반형 = 임금명세서·근로계약서·출근부)
  - 로그인 직후 사업을 고르는 단계 없음 (현재는 상단바에서 전환). 심사 문구가 "로그인 시점부터"이므로 배정 사업이 2개 이상이면 로그인 직후 선택 화면을 띄우는 것이 대응으로 명확함

### 심사② 파이프라인 중간결과물 화면 표시 — 🟡

- 이미 저장되는 것: 원본 파일, 변환 PDF(`convertedFilePath`), 추출 JSON(`extractedData`), 미비항목(`missingItems`), 보정값(`reviewedData`)
- 필요: 문서 상세 화면에서 **수집 → 변환 → 추출 → 규칙판정 → 실무자 확인** 단계별 결과를 순서대로 보여주는 뷰

### 심사③ 예외사항·암묵지 별도 섹션 — 🔴

- 필요: `exceptionRule`·`riskFlag`를 실무자가 직접 추가·수정·비활성화하는 **별도 메뉴** ("예외규칙 관리")
- 각 규칙에 출처(지침 조항 / 실무 경험 / 상위기관 회신), 등록자, 등록일, 적용 사업을 기록 → 논문의 규칙 출처·버전관리 표와 연결

### 심사④ 사용자 사용후기 인터뷰 확보 — 🔴

- 전제: 실무자가 직접 써볼 수 있는 테스트 버전
- 막는 요소:
  - 프로덕션 패키징 미완 (Electron 내 NestJS 동봉 구동)
  - `synchronize`가 production에서 꺼지는데 마이그레이션이 없음 → 배포본에서 스키마 생성 실패 위험
  - 테스트 관리자 계정(`admin`) 잔존
- 대안: 가이드 문구대로 "기관 내부 서버 1대 + 브라우저 접속" 방식이면 Electron 패키징 없이도 테스트 가능 → 테스트 방식부터 결정 필요
