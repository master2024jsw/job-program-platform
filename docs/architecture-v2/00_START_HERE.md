# 잡도리 AI Architecture v2 — 먼저 읽어주세요

작성일: 2026-10-15 · **현재 코드 점검을 바탕으로 만든 제안 설계 패키지입니다. 프로그램 수정본이나 설치 파일이 아닙니다.**

## 1. 결론부터

**기존 프로그램은 살리고, ‘누가 어느 사업에 참여해서 어떤 신청을 했고, 무엇을 근거로 처리했는가’를 연결하는 구조를 추가하는 것이 이번 제안입니다.**

React나 NestJS를 다른 것으로 바꾸는 계획이 아닙니다. CiviCRM 코드를 통째로 가져오는 계획도 아닙니다. 현재 잘 나눈 기업 원장과 사업별 기업 정보를 유지하면서, 참여기록·심사 건·버전과 이력을 더합니다.

`사업 # 어느 연도, 어느 사업인가?
 └─ 기업의 사업참여 # 어느 기업이 이 사업에 참여했는가?
 └─ 사람의 사업참여 # 누가, 어떤 기간과 조건으로 참여했는가?
 └─ 심사 건 # 무엇을 신청해서 확인해야 하는가?
 ├─ 서류판본 # 어떤 버전의 증빙을 봤는가?
 ├─ 추출값 # AI 또는 담당자가 무엇을 읽었는가?
 ├─ 규칙판정 # 어떤 지침으로 무엇을 대조했는가?
 └─ 사람결정 # 누가 왜 승인·보완·반려했는가?
`
**예외:** 기업 적격심사는 아직 참여자가 없어도 시작할 수 있습니다. 위 흐름도는 참여자 심사의 예이고, 기업 심사는 ‘기업의 사업참여 → 심사 건’으로 바로 이어집니다.

## 4. 이전 제안에서 이번에 구체화한 부분

| 항목 | 이번 문서의 결정 | 쉬운 설명 |
| --- | --- | --- |
| Worker를 Person으로 즉시 변경 | **하지 않음.** Participation부터 추가 | 이름부터 크게 바꾸면 기존 입력·메일·엑셀이 동시에 깨질 수 있습니다. |
| Case를 나중에 추가 | **최소 WorkCase는 먼저 추가** | 검증과 서류가 무엇에 속하는지 처음부터 정해야 합니다. |
| Document에 caseId 하나만 추가 | **CaseDocument가 특정 서류 버전을 연결** | 하나의 서류가 여러 심사에 쓰일 때도 판본과 근거를 구별합니다. |

## 5. 사용자가 확인하면 되는 결정 다섯 가지

| 결정 | 제안 기본값 | 달라지면 생기는 영향 |
| --- | --- | --- |
| 사용 방식 | 우선 한 PC 설치형 검증 | 여러 PC가 동시에 써야 한다면 M0에서 기관 서버형으로 바꿉니다. 두 방식을 동시에 급히 만들지 않습니다. |
| 1차 사업 | 현장실습훈련 중심 | 다른 사업은 입력 구조와 실제 지침을 추가 검증해야 합니다. |
| 지급·적격 규칙 원문 | 사용자 확인 전 미발행 | 금액과 연령·기산일을 문서 예시에서 추측하지 않습니다. |
| 최종 승인자 | 사업별 승인권을 명시적으로 배정 | 개발자 계정이나 ADMIN 역할이 자동으로 실무 승인권이 되지 않습니다. |
| 외부 AI에 보낼 자료 | 기본 차단, 우선 합성자료 | 실자료를 쓰려면 전송 범위·승인·마스킹·보존조건을 확인해야 합니다. |

기존 내부 문서의 11월 14일 목표는 현시점 확정 일정인지 확인하지 않았습니다. 일정이 촉박하면 한 사업의 검토 흐름부터 줄여서 완성하고, 근거·권한·데이터 보존은 생략하지 않습니다. [J02](https://github.com/master2024jsw/job-program-platform/blob/d9dc635a04ff5c76a8ef544547935a79b6ec770c/docs/04_%ED%98%84%ED%99%A9_%EA%B0%AD%EB%B6%84%EC%84%9D.md)

## 7. 무엇이 완료된 상태인가?

이 패키지에서 완료한 것은 **정적 코드 검토에 근거한 문서·데이터모델·ERD 원본·개발지시·테스트 명세 작성**입니다. 저장소 반영, DB 이관, 애플리케이션 테스트, 성능·정확도 측정은 완료한 것으로 표시하지 않습니다.
