## 0. 먼저 알아야 할 세 가지

**첫째, 업무모델의 중심은 사업이지만, 심사 처리의 중심은 ‘신청 1건’입니다.** ‘어느 사업인가’만 알아서는 부족합니다. ‘어느 기업의 어떤 참여자가 어느 기간·회차에 무엇을 신청했는가’가 있어야 서류와 판정이 연결됩니다.

**둘째, AI가 읽은 내용·프로그램의 규칙판정·사람의 최종 결정은 서로 다릅니다.** AI가 ‘문제없음’이라고 응답했어도 지원금을 지급할 수 있다는 의미가 아닙니다.

**셋째, 지금 필요한 것은 범용 ERP 완성이 아니라 현장실습훈련 한 사업의 끝까지 연결된 처리 흐름입니다.** 첨부 논문도 1차 범위를 서류 수집·구조화, 검증, 실무자 최종 검토에 집중하고 있습니다. 신사업 발굴·평가·민원은 확장 범위로 구분합니다. [P01] / [J01]

## 1. 제품 정의와 이번 개발 범위

### 1.1 제품 정의

‘일자리사업 수행기관 담당자가 증빙서류를 수집하고, 필요한 정보를 추출하고, 지침과 대조하고, 검토·보정 후 결정한 근거를 보존하는 행정 검토 지원 시스템’으로 정의합니다.

정부 전산시스템을 대체하거나, 금융기관에 직접 이체하거나, 확인되지 않은 자격 정보를 자동 승인하는 시스템으로 정의하지 않습니다.

### 1.2 범위 구분

| 구분 | 이번에 구현할 내용 | 쉬운 설명 |
|---|---|---|
| 기존 기능 유지 | 로그인, 기업 원장, 사업별 기업 정보, 근로자 입력, 엑셀, 메일, 문서 업로드 | 이미 만든 기능을 최대한 살립니다. 다만 잘못된 동작이나 권한 우회까지 보존하지는 않습니다. |
| v2 핵심 | 사업 범위, 참여기록, 심사 건, 문서 버전, 추출·판정·수정·승인 이력 | 흩어진 기능들을 한 신청 건으로 묶습니다. |
| v2 신뢰성 | 재시도 가능한 처리, 중복 방지, 백업·복구, 운영 마이그레이션, 전송 통제 | 오류가 나도 자료가 사라지거나 두 번 처리되지 않게 합니다. |
| v2 후속 | 지원금 정책 기반 산정, 메일 보완요청 연결, 규칙 관리 화면 | 핵심 검토 흐름이 안정화된 뒤 붙입니다. |
| 보류 | 범용 워크플로 편집기, CRM 전체 통합, 민원 RAG, 평가 자동화, 다기관 SaaS | 논문과 첫 실무 검증의 범위를 과도하게 늘리지 않습니다. |

**완료의 정의:** 메뉴가 있다는 것이 아니라, 합성 서류 한 묶음을 `접수 → 분류 → 추출 → 교차검증 → 실무자 보정 → 재검증 → 최종 결정 → 근거 조회`까지 처리하고, 실패·재시도·권한·복구 테스트를 통과한 상태입니다.

## 2. 용어를 업무 언어로 읽기

| 개발 용어 | 이 프로그램에서의 의미 | 예시 |
|---|---|---|
| `Business` | 연도와 유형을 가진 수행사업 | 2026년 현장실습훈련 사업 |
| `Company` | 회사 자체의 기본 원장 | 예시기업 A의 이름·연락처 |
| `CompanyBusiness` | 그 회사가 그 사업에 참여한 기록 | 예시기업 A × 2026년 사업 |
| `Worker` | 기존 근로자 정보. 초기에는 사람 원장 역할을 유지 | 예시참여자 A라는 사람 |
| `Participation` | 사람이 특정 사업·기업에 참여한 기록 | 예시참여자 A의 2026년 참여 이력 |
| `WorkCase` | 심사해야 할 행정 신청 한 건 | 기업 적격심사, 참여자 적격심사, 1회차 지원금 심사 |
| `DocumentVersion` | 심사에 사용한 특정 버전의 서류 | 수정 전 근로계약서 1판, 수정 후 2판 |
| `ExtractionRun` | 서류에서 정보를 읽어낸 한 번의 실행 | AI가 1판에서 추출한 입사일과 급여 |
| `PolicyVersion` | 출처와 적용시점이 고정된 지침·규칙 묶음 | 검토·발행한 사업 규칙 1.0 |
| `ValidationRun` | 특정 입력과 정책으로 검증한 한 번의 실행 | 10월 15일 오전의 검증 결과 |
| `ReviewDecision` | 실무자의 최종 결정 기록 | 보완요청, 보류, 승인, 반려 |
| `Activity` | 업무에서 실제로 일어난 일을 남긴 기록 | ‘보완요청 메일 발송’, ‘담당자 검토 완료’ |
| `Job` | 오래 걸리는 작업을 맡아 진행하는 처리 기록 | HWP 변환·AI 분석·메일 수집 |
| `Migration` | 기존 데이터를 보존하며 DB 구조를 바꾸는 절차 | 기존 근로자를 새 참여기록에 연결 |
| `Idempotency` | 같은 요청이 반복돼도 한 번의 처리 효과만 남기는 성질 | 승인 버튼을 두 번 눌러도 승인 1건 |

## 3. 핵심 설계 결정

| ID | 제안 결정 | 왜 필요한가 / 쉬운 설명 |
|---|---|---|
| ADR-01 | Electron + React + NestJS + TypeORM + SQLite 유지 | 스택 교체보다 현재 업무 관계를 정리하는 편이 변경 범위가 작습니다. |
| ADR-02 | 첫 검증 배포는 `LOCAL_DESKTOP`를 제안 기본값으로 둠 | 우선 한 PC에서 설치·실행·백업까지 끝내기 위한 기준입니다. 다인 사용이 필수면 M0에서 서버형으로 변경합니다. |
| ADR-03 | 한 설치본 = 한 운영기관, 여러 수행사업 | 처음부터 여러 기관의 데이터를 같은 서비스에 넣는 SaaS를 만들지 않습니다. 기관 정보와 접근 경계는 명시적으로 둡니다. |
| ADR-04 | Worker 전체 이름 변경 대신 Participation 추가 | 기존 API·엑셀·메일의 호환성을 지키면서 사람과 참여 이력을 분리합니다. |
| ADR-05 | 최소한의 WorkCase를 초기 단계에 추가 | 문서·검증·승인이 어느 신청 건의 일인지 먼저 정해야 뒤의 테이블을 다시 뜯어고치지 않습니다. |
| ADR-06 | 문서 버전·검증 실행·승인기록은 덮어쓰지 않음 | 과거 판단의 근거가 새 자료 때문에 바뀌지 않게 합니다. |
| ADR-07 | AI는 추출과 관찰, 규칙엔진은 대조, 사람은 결정 | 세 역할을 구분해야 오류 원인을 찾고 책임 있는 검토를 할 수 있습니다. |
| ADR-08 | 정책은 초안 → 검증 → 발행, 발행 후 불변 | 지침 파일을 수정했다고 과거 승인 근거가 조용히 바뀌면 안 됩니다. |
| ADR-09 | 기존 테이블 삭제·일괄 이름 변경은 마지막 | 추가 → 데이터 연결 → 읽기 전환 → 쓰기 전환 → 검증 순서입니다. |
| ADR-10 | 외부 AI 전송은 기본 차단 | 실제 자료에 사용할 수 있는 조건을 확인하기 전에는 합성자료로만 검증합니다. |

현재 소스에 ADR-01의 기본 구성이 있고, `CompanyBusiness` 분리도 구현되어 있습니다. 나머지 결정은 이번에 제안하는 변경이며 이미 구현된 것으로 보고하지 않습니다. [J04] / [J05] / [J10] / [J16]

## 4. 기술 구성과 폴더 구조

### 4.1 기본 구성

```text
Electron Desktop                   # 설치·서버 시작·창 생성·종료를 맡는 실행 껍데기
    └─ React Renderer              # 사용자가 보는 화면. DB를 직접 읽지 않음
           └─ NestJS API           # 로그인·권한·심사·저장의 유일한 진입점
                ├─ 업무 모듈       # 사업·기업·참여기록·심사·지원금
                ├─ 검증 서비스     # 출처가 정해진 규칙으로 대조
                ├─ Job 실행기      # 변환·분석·수집 같은 긴 작업
                ├─ SQLite          # 원장과 처리 이력 저장
                └─ DATA_DIR        # 원본·변환본·검토용 파일 저장
```

**중요:** Electron 메인 프로세스에서만 돌아가야 하는 UI 기능과, 서버에서 처리할 업무 기능을 섞지 않습니다. 프론트엔드가 SQLite 파일이나 Gemini 키를 직접 다루지 않게 합니다.

### 4.2 기존 폴더를 유지하며 추가할 모듈

```text
apps/server/src/
  common/                         # 오류 형식·공통 타입. 업무 로직을 모두 넣는 곳 아님
  database/                       # DataSource·마이그레이션·DB 상태점검
  modules/
    auth/                         # 기존 유지 + 기관·사업 접근 검사
    businesses/                   # 기존 사업·담당자 배정 유지
    companies/                    # Company·CompanyBusiness 유지
    workers/                      # 기존 사람 원장과 호환 API 유지
    participations/               # 신규: 사업별 참여기록
    cases/                        # 신규: 심사 건·상태전이·업무 이력
    documents/                    # 기존 확장: 접수·버전·추출·보정
    policies/                     # 신규: 지침 버전·필수서류·규칙 발행
    validation/                   # 신규: 규칙 실행·판정·입력 스냅샷
    review/                       # 신규: 최종 결정과 변경 이력
    jobs/                         # 신규: 재시도·처리상태·임대시간
    mail/                         # 기존 유지 + 심사 건 연결·중복 발송 통제
    mail-collector/               # 기존 유지 + 접수 원장
    subsidy/                      # 기존 산정 보존 + Claim·정책 기반 계산
    announcements/                # 유지, 이번 핵심 범위에서는 확장하지 않음

apps/renderer/src/
  api/                            # 기존 API 래퍼와 v2 요청 경로
  auth/                           # 로그인·현재 사업 UI 상태
  pages/                          # 기존 메뉴 유지, 단계적으로 새 상세 화면 연결
  features/cases/                 # 심사 건 목록·상세·결정 화면
  features/documents/             # 원본/추출값 비교, 서류 연결
  features/policies/              # 규칙 초안·검증·발행 화면

packages/shared/src/
  types/                          # 화면과 API가 공유하는 계약 타입
  schemas/                        # 신규: 순수한 데이터 구조 정의
```

**주석:** 폴더를 한꺼번에 옮기라는 지시가 아닙니다. 각 단계가 끝날 때 필요한 모듈만 추가합니다. CiviCRM의 PHP 구조나 수많은 범용 기능을 복제하지 않습니다. 새 서비스끼리 서로의 Repository를 직접 사용하지 않고 공개 서비스 메서드로 연결합니다. 순환 의존을 `forwardRef`로 반복해서 숨기지 않습니다.

### 4.3 의존 방향

`Controller → Application Service → Domain/Policy → Repository/Adapter`를 기본으로 합니다. 여기서 Adapter는 AI·메일·파일변환처럼 외부 기능을 교체할 수 있게 감싼 연결부입니다.

규칙엔진은 DB·HTTP·Gemini를 직접 호출하지 않는 순수 계산기로 둡니다. 검증에 필요한 자료를 모으는 역할은 별도 입력 구성기가 맡습니다. 이렇게 해야 합성 입력만으로 규칙을 반복 테스트할 수 있습니다.

## 5. 실제 업무 흐름

### 5.1 기업 적격 확인

기업을 원장에 등록 → 해당 사업의 `CompanyBusiness`를 ‘접수’ 상태로 생성 → `COMPANY_ELIGIBILITY` Case 생성 → 서류 연결 → 추출·검증 → 실무자 결정.

기업이 사업에 연결되어 있다는 사실은 적격 승인이나 협약 체결을 뜻하지 않습니다. 기업 원장은 기존에 있어도 새 연도의 심사 건은 새로 생성합니다.

### 5.2 참여자 적격 확인

기존 Worker를 선택하거나 신규 등록 → 해당 기업·사업의 Participation 생성 → `PARTICIPANT_ELIGIBILITY` Case 생성 → 신청서·자격서류 연결 → 검증·최종 결정.

같은 사람이 다른 연도·다른 사업에 참여하면 기존 Worker를 재사용하되 Participation을 새로 만듭니다. 동일 사업 재참여 가능 여부는 별도 지침 규칙으로 판단합니다.

### 5.3 지원금 신청 서류검증

Participation 선택 → 기간·회차가 있는 SubsidyClaim 생성 → `SUBSIDY_VERIFICATION` Case에 연결 → 해당 기간의 서류 선택 → 규칙 검증·산정 → 실무자 승인 → 지급 전 확인 목록 출력.

**지급은 별도 행위입니다.** 심사 승인만으로 `paidAmount`나 지급일을 채우지 않습니다. 정부시스템 입력·이체는 기존 사람 업무로 남기고, 확인된 지급 사실을 별도로 기록합니다.

## 6. 핵심 데이터 관계

```text
기관 ─ 사업 ─ CompanyBusiness ─ 기업
           └─ Participation ─ Worker(사람)
                     │
                     └─ WorkCase(참여자/지원금 심사)
CompanyBusiness ────────── WorkCase(기업 심사)
                               │
                               ├─ CaseDocument ─ DocumentVersion ─ FileAsset
                               │                       └─ ExtractionRun
                               ├─ FieldCorrection
                               ├─ ValidationRun ─ ValidationFinding
                               │        └─ PolicyVersion
                               ├─ ReviewDecision
                               ├─ Activity
                               └─ SubsidyClaim(지원금 심사인 경우)
```

**기업 심사에는 참여자가 아직 없을 수 있습니다.** 따라서 모든 Case를 Participation 아래에만 두는 설계는 사용하지 않습니다.

**한 서류를 여러 심사에서 다시 참고할 수 있습니다.** 따라서 Document에 `caseId` 하나만 고정하지 않고, `CaseDocument`가 어느 버전을 어떤 심사에 사용했는지 연결합니다. 같은 기관·같은 사업 안에서 명시적으로 연결하며, 다른 사업으로 자동 공유하지 않습니다.

전체 관계도는 `diagrams/domain.mmd`, 필드와 제약은 `05_Data_Dictionary.md`를 기준으로 합니다.

## 7. 기존 Worker를 안전하게 확장하기

현재 Worker는 이름·생년월일뿐 아니라 회사·급여·계약·입퇴사일을 함께 담고 있습니다. 사업 ID는 없습니다. [J09]

| 단계 | 변경 | 쉬운 설명 |
|---|---|---|
| 추가 | Participation 테이블을 추가하고 기존 Worker ID를 참조 | 근로자 원장을 지우지 않고 참여 이력 장부를 하나 더 만듭니다. |
| 분리 | 급여·계약·참여기간의 신규 원본은 Participation으로 이동 | A사업의 급여를 수정해도 B사업 이력이 바뀌지 않게 합니다. |
| 호환 | 기존 `/workers` 요청을 현재 사업의 Participation과 결합해 응답 | 기존 화면을 한 번에 버리지 않고 연결합니다. |
| 통제 | 회사·계약·급여의 v2 쓰기는 Participation 서비스만 수행 | 두 테이블에 서로 다른 값이 따로 저장되는 일을 막습니다. |
| 정리 | 검증 후 Worker의 사업 종속 필드를 사용 중단 | 즉시 삭제하지 않고 이전 데이터와 비교할 기간을 둡니다. |
| 후속 | 필요할 때 Worker → Person으로 이름 정리 | 이름 변경은 구조 안정화 이후입니다. |

**금지:** 이름+생년월일이 같다는 이유만으로 사람을 자동 병합하지 않습니다. 신규 Participation에 회사·사업이 불분명하면 미연결 상태로 남기고 확인받습니다. 한 기업이 참여한 사업이 하나라는 사실만으로 모든 과거 근로자가 그 사업 참여자였다고 확정하지 않습니다.

## 8. 심사 건의 상태와 승인 규칙

### 8.1 업무 상태

| 상태 | 뜻 | 진입 조건 |
|---|---|---|
| `INTAKE` | 접수·소속 정리 중 | 기업/참여기록/서류가 아직 모두 확정되지 않아도 가능 |
| `READY` | 검증을 요청할 준비 완료 | 사업·대상·정책 버전·선택한 증빙 범위가 확인됨 |
| `REVIEW_REQUIRED` | 실무자 검토 대기 | 검증 실행이 완료되어 결과가 저장됨 |
| `SUPPLEMENT_REQUIRED` | 보완 요청 | 담당자가 미비자료 또는 확인 필요사항을 기록 |
| `HELD` | 보류 | 기술 실패 또는 외부 확인 등을 이유로 당장 결론 내리지 않음 |
| `APPROVED` | 승인 | 권한 있는 사람이 최신 입력과 근거를 확인하고 승인 |
| `REJECTED` | 반려 | 권한 있는 사람이 사유를 남겨 반려 |
| `CANCELLED` | 신청 취소 | 신청 취소 사유·처리자를 기록 |

변환 중·AI 분석 중·재시도 대기는 Case의 업무 상태가 아니라 Job의 기술 상태로 표시합니다. Case가 `READY`인 동안 ‘AI 분석 중’ 배지를 별도로 보여줄 수 있습니다.

### 8.2 반드시 지킬 불변 조건

1. 기업 심사는 `companyBusinessId`가 필수이고 `participationId`는 비어 있어야 합니다. 참여자·지원금 심사는 둘 다 필수이며 서로 같은 회사·사업을 가리켜야 합니다.
2. Case·참여기록·문서·정책·사용자 기관이 맞아야 합니다. 클라이언트가 보낸 기관 ID를 권한 근거로 믿지 않습니다.
3. 규칙 전체가 PASS여도 사람이 승인하기 전에는 APPROVED가 아닙니다.
4. AI 오류·자료 없음·분석 미실행은 부적격이나 적격이 아니라 판정 불가입니다.
5. 승인한 뒤 증빙 버전·확정값·적용정책이 바뀌면 재검토 절차를 거칩니다. 기존 승인 이력은 보존합니다.
6. 승인된 근거 자료는 일반 삭제 API로 지울 수 없습니다. 오등록·취소·보존기간 종료는 별도 통제 절차입니다.
7. 모든 상태 변경은 서버의 전용 명령 메서드를 통합니다. 일반 PATCH로 `status=APPROVED`를 넣어 우회할 수 없습니다.

### 8.3 원자적 승인

승인 API는 한 DB 트랜잭션 안에서 다음을 처리합니다.

```text
요청자의 기관·사업·승인권한 확인
  → expectedDataRevision / version 일치 검사
  → 최신 ValidationRun의 inputHash·정책·문서 버전 일치 검사
  → 필수 확인 항목과 미해결 차단조건 검사
  → ReviewDecision 생성
  → Case 상태 및 version 갱신
  → Activity 및 감사 이벤트 기록
  → 모두 성공하면 저장, 하나라도 실패하면 모두 취소
```

검증을 아직 실행하지 못한 단계에서도 담당자는 보류·보완 사유를 남길 수 있습니다. 이때 ReviewDecision의 validationRunId와 검증 해시는 비어 있을 수 있습니다. 다만 APPROVED/REJECTED에는 완료된 실제 ValidationRun과 최신 입력·정책의 일치가 필수입니다. 검증 전 결정을 저장하려고 가짜 검증 결과를 생성하지 않습니다.

**주석:** 담당자 A가 서류를 고치는 동안 담당자 B가 이전 화면으로 승인하면 `409 STALE_REVIEW`를 반환합니다. 버튼 비활성화만으로 중복 승인을 막지 않습니다. `Idempotency-Key`와 조건부 갱신을 같이 사용합니다.

## 9. 문서 파이프라인

### 9.1 처리 순서

`접수 원장 → 원본 저장 → 소속 후보 확인 → 문서/페이지 분류 → 변환 → 전송정책 확인 → 추출 → 구조 검증 → Case 입력 구성 → 규칙 검증 → 실무자 검토`

| 단계 | 저장할 결과 | 쉬운 주석 |
|---|---|---|
| 접수 | 출처, 수신 시각, 메시지·첨부 식별자 | 같은 메일을 다시 읽어도 접수 사실을 중복 생성하지 않습니다. |
| 원본 | FileAsset, 해시, 파일크기, MIME 검사 결과 | 파일 이름이 같아도 내용이 같은지 별도로 확인합니다. |
| 분류 | DocumentType, 회사/참여기록 후보, 페이지 범위 | 한 PDF에 여러 사람·여러 서류가 들어 있을 수 있습니다. |
| 변환 | 변환본 경로, 변환기 버전, 성공·실패 | HWP 프로그램이 없으면 무엇이 부족한지 표시합니다. |
| 추출 | ExtractionRun, 스키마·모델·프롬프트 버전, 값·근거 | AI를 다시 실행해도 이전 결과를 지우지 않습니다. |
| 검증 | 입력 스냅샷, 규칙별 결과, 정책 버전 | 어떤 자료로 어떤 규칙을 실행했는지 보존합니다. |
| 검토 | 수정값·사유·담당자·시각, 최종 결정 | 사람이 바꾼 부분을 추적합니다. |

### 9.2 한 파일과 한 서류를 구분

하나의 PDF가 신청서 2쪽 + 계약서 3쪽이면 FileAsset은 하나를 재사용할 수 있지만, 논리 Document와 페이지 범위는 둘로 나눕니다. 첫 버전에는 담당자가 페이지 범위를 지정할 수 있도록 합니다. AI 자동 분할은 후속 기능입니다.

HWP·이미지는 먼저 내부에서 PDF로 표준화한 뒤 해당 범위를 선택합니다. 추출·외부 전송은 선택된 범위로 제한합니다. 한 사람의 계약서를 분석하려고 다른 사람의 개인정보가 있는 전체 파일을 보내지 않습니다. 변환 과정에서 페이지 번호가 바뀌면 원본-변환본 대응을 저장하거나 ‘대응 미확인’을 표시합니다.

### 9.3 서류와 첨부 누락 판단

AI의 `missingItems`는 관찰 정보일 뿐입니다. 필수서류 충족 여부는 아래 조건으로 판정합니다.

`사업유형 + 지침버전 + 심사단계 + 참여유형 + 대상 + 신청기간`에 맞는 요구서류 목록과, Case에 실제 연결된 적절한 버전의 서류를 비교합니다.

서류 파일이 있다는 사실, 내용 추출이 성공한 사실, 지침을 충족한 사실은 각각 별개입니다. 같은 유형의 서류가 두 개이고 어느 것이 적용본인지 모호하면 최신 날짜만 보고 자동 선택하지 않고 확인을 요청합니다.

### 9.4 추출값의 계약

```typescript
// 아래는 구현 명세용 타입 예시입니다. 기존 프로젝트에 바로 붙여넣는 완성 코드가 아닙니다.
interface ExtractedField {
  key: string;                        // 예: contract.startDate. 서류별 스키마에 정해진 이름
  value: string | number | boolean | null; // 읽은 값. 못 읽으면 null, 임의의 0이나 빈 문자열로 채우지 않음
  evidence: {
    documentVersionId: string;         // 이 값이 어느 서류 버전에서 나왔는가
    page: number | null;              // 원문 위치를 확인할 수 없으면 null
    quote: string | null;             // 검토에 필요한 짧은 원문 근거
  };
  modelConfidence: number | null;      // 모델의 자기평가일 수 있음. 검증된 정답확률로 취급하지 않음
  verification: 'UNCONFIRMED' | 'CONFIRMED' | 'CORRECTED'; // 사람의 확인 상태
}
```

AI가 반환한 JSON은 서버에서 서류별 스키마로 다시 검사합니다. 추가 필드·잘못된 날짜·배열 대신 문자열·말이 되는 것처럼 보이는 빈 값은 검증 오류로 분류합니다. 원본문서 안의 ‘지침을 무시하라’ 같은 문장은 입력자료로만 취급하고 도구 실행·외부 요청의 지시로 사용하지 않습니다.

## 10. 지침과 검증엔진

### 10.1 정책 묶음

PolicyVersion에는 사업유형·지침연도·버전·효력기간·출처·확인자·발행시각·내용 해시를 둡니다. 필수서류 목록과 추출 스키마 버전, 검증 규칙을 함께 묶어 저장합니다.

초안 JSON 편집 → 스키마 검사 → 합성 테스트 실행 → 실무자 내용 확인 → 권한자의 발행 순서입니다. **발행한 버전은 수정하지 않고 새 버전을 만듭니다.** 새 버전 발행은 과거 Case에 자동 소급 적용하지 않습니다.

규칙의 기준일은 무조건 오늘이 아닙니다. 입사일·참여개시일·신청일 등 무엇을 쓸지 규칙별로 출처와 함께 정합니다. ‘가장 최근 연도’만으로 정책을 고르지 않습니다.

### 10.2 논문 용어를 유지하는 네 가지 규칙

| 유형 | 하는 일 | 제한 |
|---|---|---|
| `crossCheck` | 두 개 이상 서류의 값 비교 | 비교 대상이 없거나 여러 개로 모호하면 통과하지 않음 |
| `calcRule` | 날짜·기간·금액 계산 | 기산일·일수 규칙·상한·반올림이 확인되어야 함 |
| `exceptionRule` | 실무 예외를 별도 검토 경로로 전달 | 담당자의 경험만으로 공식 요건을 자동 무효화하지 않음 |
| `riskFlag` | 의심 또는 현장 확인 필요 신호 표시 | 신호 자체를 부정수급 확정으로 표시하지 않음 |

이는 첨부 논문의 분류를 유지한 것입니다. 실제 규칙 내용은 원문·상위기관 회신·실무 사례의 근거를 구분해 확인해야 합니다. [P01]

### 10.3 규칙 실행기의 책임

입력: Case 종류, 선택된 증빙 버전, 추출/보정값, 참여기록 스냅샷, 기준일, PolicyVersion.  
출력: 규칙별 판정·사유·사용 입력·근거 위치·차단 수준.

허용 연산자는 초기에는 동등 비교, 범위 비교, 날짜 포함, 만 나이 계산, 승인된 금액식, 수동확인 요구 정도로 제한합니다. 규칙 JSON에서 임의 JavaScript, SQL, 파일 경로, 네트워크 주소를 실행하지 않습니다. `eval` 또는 동적 Function 생성은 사용하지 않습니다.

**‘코드 수정 없이 지침 반영’의 범위:** 기존 연산자로 표현되는 기준값·필수서류·적용 조건은 데이터 변경으로 반영할 수 있습니다. 새로운 판단 알고리즘이 필요하면 연산자 개발과 테스트가 추가로 필요합니다. 모든 미래 지침을 데이터 입력만으로 처리한다고 약속하지 않습니다.

### 10.4 판정 집계

| 규칙 결과 | 의미 | 최종 처리 |
|---|---|---|
| PASS | 이 규칙의 확인 가능한 조건을 충족 | 실무자 검토 대기 |
| FAIL | 확인된 입력이 기준과 불일치 | 차단 또는 반려 검토. 자동 반려 아님 |
| NEEDS_REVIEW | 예외·위험·모호한 근거 | 사람 확인 필요 |
| INSUFFICIENT_DATA | 필요한 값/서류가 없음 | 보완 또는 보류 |
| NOT_APPLICABLE | 적용대상이 아님을 확인함 | 이 규칙의 판정 대상에서 제외 |
| 실행 FAILED | 변환/API/엔진 오류 | 위 업무판정과 별도로 기술 오류 표시 |

필수 규칙이 0개 실행되거나 전부 해당 없음인 결과를 자동 PASS로 집계하지 않습니다. 필수 확인 항목의 커버리지도 같이 기록합니다. 실무상 수동 검증을 허용하는 항목은 확인근거와 담당자를 남겨야 하며, 차단 요건의 예외 적용은 정책이 허용한 별도 권한·사유·근거를 요구합니다.

| 신청한 금액 | SubsidyClaim.requestedAmountWon | 기업/참여자가 요구한 금액 |
| 규칙으로 계산한 금액 | SubsidyCalculation의 정책·입력 스냅샷 | 시스템 계산값. 기존 일할 급여 산정과 구분 |
| 사람이 승인한 금액 | ReviewDecision과 Claim의 승인 투영값 | 결정 시점의 승인금액 |
| 실제 지급한 금액 | 확인된 지급 기록 | 실제 이체나 전산처리가 확인된 금액 |

원화 금액은 정수 단위로 저장하고, 비율·일할 계산 중간값은 정밀 계산 방식과 정책상 반올림을 명시합니다. 값이 없으면 null이며, 0원과 구분합니다. JavaScript 안전 정수 범위를 검사합니다.

지원금 신청 건은 `participationId + benefitType + periodStart + periodEnd + installmentNo`의 중복을 제한합니다. 단순 고유키뿐 아니라 이미 승인된 기간과 겹치는 신청도 검사하되, 다른 지원유형의 정당한 병행 여부는 정책으로 판단합니다. 자유 입력 텍스트 `periodLabel`만으로 회차를 식별하지 않습니다.

기존 `SubsidyCalculation`은 삭제하지 않습니다. 새 `claimId`, 정책 버전, 계산식 버전, 입력 해시 연결을 추가하되 과거 기록을 사후에 공식 검증 완료로 바꾸지 않습니다. 현재 계산식의 확인 근거는 진단서 F05에 있습니다. [J17]

권한 판단 순서는 `세션 → 기관 → 사업 배정 → 실제 리소스의 사업 소속 → 기능별 capability`입니다. URL의 사업과 DB 자료의 사업이 다르면 거절합니다. 테스트에서는 기관 A/B를 함께 만들어 우회가 없는지 확인하되, 실제 다기관 SaaS 제공은 별도 범위입니다.

## 13. API 계약

### 13.1 기존 경로와 새 경로

기존 `/companies`, `/workers`, `/documents` 등은 이관 기간의 호환 경로로 보존합니다. **누락된 사업 범위까지 계속 허용하지는 않습니다.** 해당 UI와 API를 같은 단계에서 변경하고, 업무상 사업이 필요한 요청은 누락 시 400으로 명확하게 반환합니다.

새 API는 `/api/v2/businesses/:businessId/...` 아래에 두며, URL의 사업과 본문에 중복된 사업 정보가 다르면 400으로 거절합니다. `institutionId`, `reviewedBy`, 최종상태 등 서버 소유 필드는 사용자가 임의로 쓸 수 없습니다.

| 메서드·경로 | 입력/출력 요점 | 쉬운 주석 |
|---|---|---|
| POST `/api/v2/businesses/:b/participations` | workerId, companyBusinessId, 참여기간 | 사람을 해당 사업에 연결 |
| GET `/api/v2/businesses/:b/cases` | 단계·상태·담당자 필터, 페이지 조회 | 심사 대기함 |
| POST `/api/v2/businesses/:b/cases` | kind, companyBusinessId, participationId? | 새 심사 건 생성 |
| POST `/api/v2/businesses/:b/cases/:c/documents` | documentVersionId, expectedVersion | 어떤 서류 버전을 심사에 쓸지 연결 |
| POST `/api/v2/businesses/:b/documents/:d/extractions` | versionId, schemaVersion, Idempotency-Key | 분석 Job 생성, 202 반환 |
| POST `/api/v2/businesses/:b/cases/:c/validations` | expectedDataRevision, 정책 버전 확인 | 검증 Job 생성, 202 반환 |
| GET `/api/v2/businesses/:b/jobs/:j` | 상태·단계·안전한 오류 내용 | 진행률 확인. 파일 경로·비밀키 노출 금지 |
| POST `/api/v2/businesses/:b/cases/:c/corrections` | 추출실행·필드·보정값·사유·기대버전 | 보정 저장 후 기존 검증 무효화 |
| POST `/api/v2/businesses/:b/cases/:c/decisions` | runId?, expectedVersion, expectedDataRevision, inputHash?, decision, reason | 승인·반려에는 최신 완료 실행 필수. 검증 전 보류·보완만 실행 참조 생략 가능 |
| POST `/api/v2/businesses/:b/claims` | participationId, 기간·회차·유형 | Case와 Claim을 한 트랜잭션으로 생성 |
| GET `/api/v2/businesses/:b/cases/:c/report` | 판정·근거·검토기록 | 결과 보고서. 판정 불가와 미비 없음을 구분 |
| GET `/api/v2/businesses/:b/files/:id` | 자료 소속·조회권한 검사 | 원본/변환본 열기 |
| POST `/api/v2/intake/:id/assign` | 사업·대상 매핑, 기대버전 | 미분류 자료 배정. 접수 담당 권한 필요 |

성공 응답은 기존 형태를 유지합니다.

```json
{
  "success": true,
  "data": { "jobId": "example-job-id", "status": "QUEUED" }
}
```

오류는 `success:false`, `code`, `message`, `requestId`, 필요한 경우 안전한 `details`로 통일합니다. 401은 로그인, 403은 권한, 404는 허용 범위에서 자료 없음, 409는 중복/버전충돌, 422는 의미상 잘못된 입력, 503은 일시적 처리 불가로 구분합니다. 기존 클라이언트가 의도적으로 204 응답을 처리하지 못하므로 호환 API의 삭제 응답은 기존 `success:true` 형식을 유지합니다. [J15]

### 13.2 중복 요청 규칙

변경 요청의 Idempotency-Key는 `기관 + 사용자 + 명령 종류 + 키`로 고유하며 요청 본문 해시도 저장합니다. 같은 키와 같은 내용은 기존 결과, 같은 키와 다른 내용은 409입니다. 승인 중복과 Job 중복은 DB 제약으로도 방지합니다.

## 14. 화면 구성

기존 메뉴를 전면 재배치하지 않고 문서함과 지원금 메뉴에서 ‘심사 건 상세’로 진입하게 합니다. 첫 검증 기간에는 새 메뉴가 많아지는 것보다 한 화면의 처리 흐름이 연결되는 것이 중요합니다.

| 화면 영역 | 표시 내용 | 사용자의 이점 |
|---|---|---|
| 상단 | 현재 기관·사업·기업·참여자·심사 종류·기간·회차 | 다른 사업/사람의 자료를 보고 있는 실수를 줄임 |
| 단계 표시 | 접수·변환·추출·검증·검토의 현재 상태 | 어디서 막혔는지 바로 알 수 있음 |
| 왼쪽 | 원본/변환 문서, 페이지 이동 | 실제 서류를 눈으로 확인 |
| 가운데 | 추출값과 보정값, 차이 표시 | AI가 무엇을 읽고 사람이 무엇을 고쳤는지 비교 |
| 오른쪽 | 규칙 결과, 적용 조항, 입력 근거, 미비/불확실 표시 | 왜 이런 판단이 나왔는지 확인 |
| 하단 | 보완요청·보류·승인·반려, 변경 사유 | 최종 의사결정 |
| 이력 | 이전 분석·정책·수정·결정의 시간순 기록 | 인수인계와 점검 근거 |

좁은 화면에서는 세 칸을 무조건 줄이지 않고 탭/분할 보기로 전환합니다. 오류는 ‘실패했습니다’ 한 줄 대신 단계와 해결 행동을 보여줍니다. 예: ‘HWP 변환 프로그램을 찾을 수 없습니다. PDF로 다시 올리거나 설치 상태를 확인하세요.’

화면 캐시 키에는 `institutionId + businessId + resource + filter`를 포함합니다. 사업 전환 시 선택된 기업·참여자·Case·발송 대상·이전 조회 결과를 정리하고, 이전 사업 요청의 늦은 응답을 새 화면에 표시하지 않습니다. 새 상태관리 라이브러리 도입은 필수 조건이 아닙니다.

## 15. Job·메일·재시도

### 15.1 Job 상태

`QUEUED → RUNNING → SUCCEEDED` 또는 `RETRY_WAIT → RUNNING`, 최종 `FAILED` / 사용자 `CANCELLED`로 관리합니다.

Job은 입력 대상·버전·작업 종류·중복키·시도횟수·임대토큰·임대만료·마지막 오류코드·결과 참조를 저장합니다. 작업자가 중단되면 임대가 만료되어 재시도할 수 있지만, 이전 작업자가 늦게 돌아왔을 때 결과를 덮어쓰지 못하도록 임대토큰과 대상 버전을 다시 검사합니다.

DB 트랜잭션을 열어둔 채 AI·SMTP·HWP 변환이 끝나기를 기다리지 않습니다. 짧은 트랜잭션으로 작업을 등록하고, 외부 작업 후 결과를 다시 검증해 저장합니다. 초기에는 별도 Redis 없이 SQLite Job 원장과 제한된 실행 동시성으로 시작하되, 실제 부하 결과에 따라 변경합니다.

### 15.2 메일 수집

수집 완료 여부의 기준은 읽음 플래그가 아니라 접수 원장입니다. 메시지 고유키는 계정·메일함·UIDVALIDITY·UID, 첨부 고유키는 여기에 첨부 part 식별자를 더합니다. 파일 해시는 바이트 중복 판단에 쓰지만, 같은 파일이 다른 신청 건의 증빙으로 제출된 업무 의미까지 삭제하지 않습니다.

발신자와 기존 자료를 매칭해 후보를 제시합니다. 후보가 여럿이거나 검증되지 않은 발신자는 미분류로 둡니다. 제목의 Case 번호만으로 소속을 바꾸지 않습니다. 링크 토큰을 사용하더라도 만료·서명·사업·대상 일치를 확인합니다.

### 15.3 보완요청과 발송

Case의 보완사항으로 메일 초안을 만들고 담당자가 수신자·내용·첨부를 확인한 뒤 발송합니다. 자동 재발송과 예약 발송은 첫 핵심 범위에서 기본 비활성입니다.

SMTP 응답 중 연결이 끊기면 메일이 실제로 보내졌는지 불확실할 수 있습니다. 이 경우 `DELIVERY_UNKNOWN`으로 분리하고 무조건 자동 재발송하지 않습니다. 요청 중복키와 Message-ID는 추적에 쓰지만 외부 메일의 완벽한 1회 배달을 보장한다고 설명하지 않습니다.

## 16. 설치·네트워크·파일 경로

### 16.1 LOCAL_DESKTOP — 제안 기본값

Electron이 자신의 서버 프로세스를 시작하고 정상 준비를 확인한 뒤 화면을 엽니다. 서버는 loopback 주소에만 바인딩합니다. 포트를 하드코딩해 충돌을 감추지 않고, 선택한 포트와 서버 식별정보를 검증합니다.

서버가 UI를 `/app/`에서 제공하고, React Router는 `/app` 기준으로 동작하도록 제안합니다. 새 API는 `/api/v2/`, 기존 호환 API는 기존 경로를 유지합니다. **SPA의 `/companies` 화면 경로와 GET `/companies` API가 충돌하지 않도록 UI의 기본 경로를 분리합니다.** SPA fallback은 `/app/*`에만 적용하고 API 404를 HTML로 바꾸지 않습니다.

클라이언트는 현재 앱 Origin 기준 API를 사용합니다. 개발용 Vite 프록시와 배포용 경로는 각각 테스트해야 합니다. 쿠키·CORS 문제를 `webSecurity:false`로 해결하지 않습니다. 현재 Electron의 `contextIsolation:true`, `nodeIntegration:false`는 유지합니다. [J04] / [T02]

서버 실행 런타임은 M0 패키징 실험에서 확정합니다. 별도 Node 실행파일 동봉 또는 Electron utility process 중 하나를 선택하고, `better-sqlite3`·`winax`를 그 런타임과 아키텍처에 맞춰 빌드합니다. 개발 PC에 Node·한글이 설치돼 있다는 이유로 설치본에서도 실행된다고 가정하지 않습니다.

### 16.2 INSTITUTION_SERVER — 다인 사용 시 선택

서버 한 대가 API·UI·DB·파일을 소유하고 각 담당자는 HTTPS 브라우저로 접근합니다. 브라우저의 API 주소는 서버와 같은 Origin을 사용하며 `localhost:3000` 고정을 제거합니다. 서비스로 실행되므로 Electron 창 종료와 무관하게 서버가 유지됩니다.

SQLite 파일을 공유폴더에 놓고 각 PC가 직접 열게 하지 않습니다. 동시 접근은 서버 API를 통해서만 합니다. 처리량·쓰기 경합·백업 시간을 측정한 뒤 PostgreSQL 전환 필요성을 판단합니다. 이 모드를 선택하면 인증서·방화벽·세션 저장소·서버 계정·운영 백업이 추가 완료조건입니다.

### 16.3 데이터 경로와 변환기

`DATA_DIR`를 하나의 절대 경로로 확정하고 그 아래 DB·원본·변환본·임시파일·로그를 분리합니다. DB와 업로드 위치를 서로 다른 `process.cwd()` 해석에 맡기지 않습니다. 앱 설치 디렉터리에는 실자료를 쓰지 않습니다.

HWP 변환은 별도 Adapter 뒤에 두고, 허용 확장자·실제 파일 형식·용량·시간제한·프로세스 종료를 검사합니다. 매크로·비정상 파일·압축폭탄 등의 입력은 거절 또는 격리합니다. ZIP 자동 해제는 보안 제한과 테스트가 확보되기 전까지 지원 목록에 넣지 않습니다. 기존 수집 함수는 모든 첨부를 그대로 저장하므로 ‘압축 해제 완료’로 보고하지 않습니다. [J20]

| 통제 | 제안 | 쉬운 설명 |
|---|---|---|
| 외부 AI | 기본 OFF, 합성자료 테스트 우선 | 승인 전 실제 주민번호·계좌정보가 외부로 나가지 않게 함 |
| 내부 완결 모드 | 내부 추출기 또는 수동입력 Adapter 사용 | 외부 AI를 끄면 나머지 흐름도 검증할 수 있게 함 |
| 전송 허용 모드 | 목적·대상·자료 범위·변환본 검토·승인 기록 필수 | 로컬 보관과 외부 전송을 별도 선택으로 다룸 |
| 마스킹 | 실제 전송본의 이미지·텍스트층·주석·메타데이터 확인 | 화면에서 검게 보이는 것만으로 숨겨졌다고 간주하지 않음 |
| 로그 | requestId·단계·오류코드 중심, 원문·비밀키 출력 금지 | 오류를 고치려고 개인정보를 로그에 쌓지 않음 |
| 저장 | OS 접근권한, 장치 암호화 정책, 백업 접근통제 | SQLite를 쓴다고 파일이 자동 암호화되는 것은 아님 |
| 원본 삭제 | 승인 근거는 일반 삭제 불가, 보존정책 확정 후 별도 처리 | 실수로 지워 점검 근거가 없어지는 것을 막음 |
| 감사 | 업무 수정·정책 발행·승인·내보내기의 append-only 기록 | 누가 무엇을 했는지 남김. 로컬 관리자까지 막는 절대 불변 저장소는 아님 |

외부 AI 정책·법적 근거·보관기간은 이 설계서에서 임의 확정하지 않습니다. 개인정보 없는 합성자료로 품질을 확인한 것과 실자료 운영 승인을 혼동하지 않습니다.

## 18. 기존 DB를 옮기는 절차

### 18.1 원칙

운영 DB를 열자마자 구조를 자동 변경하지 않습니다. `synchronize`를 끄는 것만으로 끝나지 않으며, 빈 DB용 생성 경로와 기존 DB용 변환 경로가 모두 있어야 합니다. 기존 DB의 실제 스키마는 아직 확인하지 않았으므로 확정된 운영 이관 SQL을 이 문서에 포함하지 않습니다. [J10]

### 18.2 단계

| 순서 | 수행할 작업 | 통과 조건 |
|---|---|---|
| 1 | DB·업로드·관련 설정의 위치와 버전 확인 | 동일한 설치본의 자료임을 확인 |
| 2 | Job·메일·쓰기 일시 중지, 일관된 백업 생성 | 백업을 별도 위치에서 실제 복구 가능 |
| 3 | 테이블·컬럼·인덱스·건수·누락 파일 목록 조사 | 기준선 fingerprint와 진단 보고서 생성 |
| 4 | 복제 DB에 새 테이블·컬럼 추가 | 기존 테이블·ID·파일 손실 없음 |
| 5 | Worker → Participation의 명시적 매핑 | 확정된 매핑만 이관, 모호한 자료는 보류 |
| 6 | DocumentVersion·레거시 추출값 스냅샷 생성 | 원본·기존 검토값 보존, 근거 미확인 상태 명시 |
| 7 | 기존 산정을 레거시 기록으로 연결 | 공식 검증·승인 이력을 소급 생성하지 않음 |
| 8 | v2 읽기 전환 → 비교 → 쓰기 전환 | 데이터 건수·금액·관계·권한 테스트 통과 |
| 9 | 시범 운영과 복원 연습 | 장애 시 앱 버전과 데이터 세트를 함께 되돌릴 수 있음 |
| 10 | 별도 승인 후 레거시 컬럼 정리 | 유지기간·백업·회귀 테스트 충족 |

**금지:** `business_id IS NULL`인 모든 행을 한 사업 ID로 일괄 UPDATE하지 않습니다. 루트 실행계획에 있던 이 방식은 실제 자료가 단일 사업임을 확인했을 때만 조건부로 검토할 수 있습니다. 이번 설계는 매핑 근거 없는 자동 배정을 기본값으로 두지 않습니다. [J03]

### 18.3 백업과 롤백

SQLite의 지원되는 백업 API를 이용하거나 쓰기를 중지하고 연결을 정상 종료한 상태에서 일관된 DB 사본을 만듭니다. WAL 사용 중 DB 파일 하나만 임의 복사하는 방식을 정식 백업으로 삼지 않습니다. [T03]

DB·파일 저장소·스키마 버전·앱 버전·파일 해시 목록을 같은 백업 단위로 관리합니다. 외부 서비스 비밀키는 문서나 저장소에 넣지 않고 별도의 승인된 비밀정보 관리 절차를 따릅니다.

롤백은 파괴적 `down` SQL보다 검증된 이전 앱과 백업 세트 복원을 기본으로 합니다. 이관 후 새 자료가 생긴 경우 복원만 하면 손실될 수 있으므로 신규 쓰기 중지·변경분 보존·재적용 계획을 먼저 세웁니다.

## 19. 개발 단계와 완료 게이트

| 단계 | 목표 | 통과해야 다음 단계로 진행 |
|---|---|---|
| M0 | 실제 상태·배포 모드·테스트 기준선 확인 | 실행 로그, 현재 스키마, 보존 대상, 미결정 사항 문서화 |
| M1 | 백업·마이그레이션 기반과 사업 접근 통제 | 빈 DB/복제 DB 생성·이관, 접근 부정 테스트 통과 |
| M2 | Participation·WorkCase·최소 Activity | 기업/참여자/지원금 심사 생성과 소속 일치 검증 |
| M3 | 문서 버전·접수 원장·추출 Job | 중복·실패·재시도·서류 범위·기존 검토 보존 확인 |
| M4 | 정책·규칙엔진·판정 이력 | 합성 사례에서 근거와 버전이 재현되며 자료 없음 처리 정확 |
| M5 | 검토 화면·보정·원자적 최종 결정 | 과거 화면 승인 거절, 보정 후 재검증, 원본 대조 가능 |
| M6 | 지원금 Claim·정책 산정·보완메일 | 지침 확인값만 사용, 중복회차·불명확 발송 통제 |
| M7 | 선택한 방식의 배포·보안·복구 검증 | 비개발 PC에서 처리 한 사이클·백업·복원·재시작 통과 |
| M8 | 실무자 테스트·논문 결과 정리 | 측정표·오류·사용후기·버전이 연결된 결과 확보 |

M3/M4의 개발 테스트에는 가짜 AI Adapter와 합성 JSON을 사용합니다. 외부 API 비용·실자료 전송 없이도 핵심 로직을 검증할 수 있어야 합니다. 각 단계의 구체적 Claude Code 지시는 `03_Claude_Code_Playbook.md`에 있습니다.

## 20. 실무 평가와 논문에 남길 결과

| 평가항목 | 기록 방법 | 해석 주의 |
|---|---|---|
| 처리시간 | 동일 난이도 사례의 수동/시스템 시작·종료 시간, 대기시간 분리 | 인터뷰상의 예상시간과 새 실측시간을 같은 실험값처럼 합치지 않음 |
| 추출 정확도 | 항목별 정답과 추출값, 누락·오인식 구분 | JSON 형식 성공이 정보 정확도는 아님 |
| 규칙 정확도 | 담당자가 확인한 정답과 PASS/FAIL/보류 비교 | 불명확 사례를 억지로 이진 정답으로 만들지 않음 |
| 검토 부담 | 보정 항목 수, 원본 재확인 수, 잘못 통과한 건 | 속도만 빨라지고 잘못 승인하면 성공 아님 |
| 안정성 | 재시도·중복·권한·백업 복원 테스트 결과 | 데모 1회 성공을 운영 안정성으로 확대 해석하지 않음 |
| 사용자 의견 | 업무 맥락·장애·개선 요청과 사용 버전 | 후기와 객관적 성능지표를 구분 |

본 문서는 설계 산출물입니다. 여기 적힌 기능을 실제 구현·평가 결과 장에 ‘완료’로 옮기지 않습니다. 단계별 실행 증거가 생긴 항목만 개발결과에 반영합니다.

## 21. 작업 전 확인해야 할 결정

| 질문 | 제안 기본값 | 답이 없을 때의 처리 |
|---|---|---|
| 첫 사용은 개인 PC인가, 여러 PC 동시 접속인가? | LOCAL_DESKTOP | 설계·합성 테스트는 진행, 운영 배포 방식 확정은 보류 |
| 실자료가 이미 존재하는가? | 존재한다고 보수적으로 가정 | 삭제·초기화·전역 데이터 변경 금지 |
| 확정된 사업지침 원문·회신·규칙 원장이 있는가? | 미확인 | 예시 규칙은 DRAFT·운영 비활성 |
| 실제 자료를 외부 AI로 전송할 수 있는가? | 아니오 | 합성자료/수동 추출 Adapter만 사용 |
| 승인권자와 정책 발행권자는 누구인가? | 미확인 | 관리자 계정 존재만으로 실무 승인권한 자동 부여하지 않음 |
| 문서 보존기간과 삭제 권한은 무엇인가? | 미확인 | 일반 사용자의 승인 근거 영구삭제 금지 |
| 저장소의 2026-11-14 목표가 여전히 유효한가? | 참고 일정 | 검증 게이트를 생략할 근거로 사용하지 않음 |

**최종 방향:** CiviCRM의 ‘원장–업무 건–활동’ 연결 방식은 참고하되, 잡도리의 핵심 차별점인 ‘증빙 버전–정책 버전–규칙판정–실무자 결정’의 재현성을 중심으로 구현합니다. 전체를 새로 만드는 것이 아니라, 기존 기능에 안전한 연결 구조를 추가하는 계획입니다.
