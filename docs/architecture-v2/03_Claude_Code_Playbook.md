## 2. 모든 단계에 적용할 공통 규칙

다음 블록을 각 단계 지시 앞에 같이 전달하거나, 사용자의 승인 후 프로젝트 지침에 추가합니다. 기존 `CLAUDE.md`를 통째로 덮어쓰지 않습니다.

`[잡도리 AI v2 공통 개발 규칙]

A. 업무 범위
- 1차 목표는 현장실습훈련 한 사업에서 접수→추출→검증→보정→결정→이력조회가 연결되는 것이다.
- 신사업 발굴, 민원 RAG, 평가 자동화, 범용 ERP 확장은 이번 작업에 추가하지 않는다.
- Electron/React/NestJS/TypeORM/SQLite를 유지한다. 별도 승인이 없는 프레임워크 교체는 금지한다.

B. 기존 자료 보존
- 실제 운영 DB에 직접 실험하지 않는다. 먼저 복제본과 파일 백업으로 검증한다.

- 기업이 한 사업에만 속한다는 이유로 모든 과거 근로자·서류를 그 사업에 일괄 배정하지 않는다.

C. 권한과 검증
- businessId를 추가하는 것만으로 완료라고 하지 않는다. 조회·수정·다운로드·내보내기·배치에 동일 경계를 적용한다.

- 문서 버전, 추출 실행, 검증 실행, 보정, 승인 기록을 덮어쓰지 않는다.
- 명령을 한 번 더 보내도 중복 승인·중복 청구·중복 메일이 되지 않는지 확인한다.
- 한 단계의 변경을 작은 단위로 완료하고 테스트 결과를 제시한다.
- 로그·테스트 실행 없이 '정상', '완료', '100%'라고 쓰지 않는다.
- 테스트 미실행, 실패, 외부 환경 때문에 확인하지 못한 항목을 구분한다.
- 커밋과 푸시는 사용자가 별도로 승인할 때만 한다.

## 6. M2 — 사람·참여기록·심사 건 연결

`M2만 구현하라. Worker 테이블을 삭제하거나 Person으로 일괄 개명하지 마라.

1) Participation을 추가하라. workerId, businessId, companyBusinessId,
 episodeNo 및 해당 참여의 근무조건·기간을 관리한다.
2) 같은 사람의 다른 사업 참여가 급여·소속·기간을 덮어쓰지 않게 하라.
 이름+생년월일만으로 같은 사람이라고 자동 병합하지 마라.
3) WorkCase는 COMPANY_ELIGIBILITY / PARTICIPANT_ELIGIBILITY /
 SUBSIDY_VERIFICATION 세 종류로 제한한다.
4) 기업 심사는 참여자 없이 만들 수 있어야 한다. 참여자·지원금 심사는
 참여기록과 기업사업 연결이 일치해야 한다.
5) Case 작성과 최소 Activity 기록을 트랜잭션으로 저장하라.
 화면의 사업 전환으로 과거 비동기 응답이 다시 표시되지 않게 하라.
6) 기존 /workers 및 엑셀 양식은 호환 어댑터를 두어 단계적으로 전환한다.
 지원되지 않는 기존 쓰기를 조용히 무시하지 말고 명확하게 안내하라.
7) QA-009~013, QA-048~049와 M1 권한 회귀를 수행하라.

모호한 기존 데이터의 자동 배정은 하지 말고 매핑 예외목록을 보고하라.
`
**쉬운 설명:** 사람은 그대로 두고 ‘이 사람이 이번 사업에서 일하는 조건’을 별도 카드로 만듭니다. 그 카드에 기업 심사·참여자 심사·지원금 심사를 연결합니다.

## 7. M3 — 서류 접수와 버전이 남는 분석

`M3만 구현하라. 기존 업로드·문서 목록은 보존하면서 처리 기록을 추가한다.

1) FileAsset, DocumentVersion, CaseDocument, ExtractionRun을 추가한다.
 원본, 표준 PDF, 심사 범위 PDF, 외부전송용 파일을 구분한다.
2) 한 파일에 여러 사람의 서류가 있으면 페이지 분류를 지원한다.
 일부 Case 권한만 있는 사용자에게 전체 원본을 노출하지 않는다.
3) 재분석은 새 ExtractionRun을 만든다. 이전 reviewedData를 새 분석의
 검토 결과로 재사용하지 않는다. 기존 값은 LEGACY 이력으로 보존한다.
4) PENDING/FAILED/분석불가 서류를 보고서에서 '미비 없음'으로 표시하지 않는다.
5) 문서별 추출 스키마와 증거 위치를 검사한다. 값을 못 읽으면 null이다.
6) 영속 Job에 lease, 재시도 횟수, 오류코드, 입력 해시를 둔다.
 API/변환 작업 동안 DB 트랜잭션을 장시간 유지하지 않는다.
7) IMAP 메시지와 첨부별 접수키를 기록한다. 부분 실패 후 재실행이 안전해야 한다.
8) 외부 전송은 기본 OFF로 두고 모의/수동 추출 경로로 검증한다.
9) QA-014~020, QA-033~036, QA-047과 권한 회귀를 수행한다.

한 번 실제 분석에 성공한 것을 재시작·복구 검증 완료로 보고하지 마라.
`
**기존 확인 파일:** `documents/document.entity.ts`, `documents/documents.service.ts`, `documents/gemini.service.ts`, `mail-collector/mail-collector.service.ts`, `renderer/src/pages/DocumentsPage.tsx`.

**쉬운 설명:** 파일·AI 결과·사람의 수정본에 각각 날짜와 버전이 붙는 단계입니다. 오류가 발생했을 때 ‘어디까지 처리됐는가’를 확인할 수 있습니다.

## 8. M4 — 근거가 있는 규칙 검증

`M4만 구현하라. 데이터 사전의 PolicyVersion/ValidationRun/ValidationFinding을 따른다.

1) 기존 검증 인터페이스의 passed:boolean만으로 모든 상태를 표현하지 마라.
 PASS, FAIL, NEEDS_REVIEW, INSUFFICIENT_DATA, NOT_APPLICABLE을 구분한다.
 엔진 실행 오류는 별도 실행상태로 남긴다.
2) 정책은 초안/발행/폐기와 출처·버전·효력일·해시를 관리한다.
 발행 정책을 직접 변경하거나 과거 Case에 자동 소급하지 않는다.
3) 필수서류 목록, 추출 스키마, crossCheck/calcRule/exceptionRule/riskFlag를
 정책 묶음으로 관리한다. 처음에는 허용된 연산자만 제공한다.
4) 예시 policy.demo.json은 합성 테스트 전용이다. 실제 SENIOR 규칙으로 발행하지 마라.
5) 검증 입력은 Case에 선택된 문서 버전·추출 실행·보정값의 스냅샷이다.
 과거 판정을 현재 Worker 정보와 즉석 조합해 바꾸지 마라.
6) 값 없음, 비교 후보 중복, 실행 규칙 없음, 전체 해당 없음의 집계를 처리한다.
7) 검증 결과에는 ruleKey, outcome, source, evidence, reason, policyHash,
 inputHash, engineVersion, coverage를 남긴다.
8) QA-021~026, QA-032, QA-041, QA-050을 수행한다.

합성 정답 사례와 실제 지침 확인 여부를 별도로 보고한다.
`
**쉬운 설명:** AI가 읽은 값을 실제 체크리스트와 비교하는 단계입니다. ‘아직 모르겠다’는 결과를 오류나 부적격과 구별합니다.

## 9. M5 — 검토 화면과 최종 결정

`M5만 구현하라. 심사 상세는 원본/추출·보정값/판정근거/처리이력을 함께 제공한다.

1) FieldCorrection에 원래 값·새 값·CONFIRM/CORRECT·사유·작성자를 추가 기록한다.
 보정은 해당 Case에 적용하며 다른 Case/사람 원장을 자동 덮어쓰지 않는다.
2) 자료·보정·정책 변경 시 dataRevision을 올리고 이전 판정에 재검증 표시를 한다.
3) 최종 승인·반려는 전용 decisions 명령을 사용한다.
 승인에는 최신 완료된 ValidationRun, 정책, 입력 해시, 사용자 권한이 필요하다.
 검증 전 보류·보완은 runId 없이 허용할 수 있지만 승인을 대신할 수 없다.
4) expectedVersion, expectedDataRevision, Idempotency-Key를 검사한다.
 ReviewDecision, Case 상태, Activity, 감사기록은 함께 저장되거나 함께 취소된다.
5) 모든 PASS도 사람의 결정이 있어야 APPROVED가 된다.
 기술 장애/자료 부족을 적격으로 바꾸는 편의 버튼을 만들지 않는다.
6) 승인 이후 서류를 바꾸는 경우 재개 절차와 이전 결정 보존을 구현한다.
7) QA-027~031, QA-014~017, QA-048~049를 수행한다.

담당자 두 명이 동시에 보정·승인하는 충돌 시나리오 결과를 반드시 보고한다.
`
**쉬운 설명:** 사용자가 ‘어떤 원본을 보고, 어떤 값을 바꾸고, 왜 승인했는지’를 한 화면에서 확인하고 그 사실이 보존되게 합니다.

## 10. M6 — 지원금과 보완요청 연결

`M6만 구현하라. 실제 지원금 규칙이 승인되지 않았으면 합성 테스트와 준비상태까지만 만든다.

1) SubsidyClaim을 Case와 함께 생성하고 기간·회차·지원유형의 중복을 검사한다.
2) 신청액, 정책 계산액, 승인액, 실제 지급 확인액을 분리한다.
 기존 salary/30*workedDays 기록은 LEGACY로 보존하고 공식 지원금 판정으로 표시하지 않는다.
3) 정책의 기준일·비율·상한·회차·반올림·중도퇴사 처리를 실무자가 확인하지 않았으면
 계산/승인을 차단하고 POLICY_NOT_CONFIGURED로 안내한다.
4) 안내 설정과 공식 적격 규칙을 구분한다. 사업별 기본 안내개월은 초안 값일 뿐이다.
5) 보완요청 초안을 Case의 미해결 finding에서 만들고 담당자 확인 후 발송한다.
 메일 발송 의도·시도·결과를 구분하고 동일 명령의 중복 발송을 방지한다.
6) SMTP 응답이 불명확하면 DELIVERY_UNKNOWN으로 기록하고 무조건 재발송하지 않는다.
7) 실제 이체·정부 전산 등록은 자동 수행하지 않는다.
8) QA-037~041, QA-025, QA-028~030과 기존 메일 회귀를 수행한다.

운영 정책이 미확정이면 '산정 완료' 대신 남은 결정사항을 보고한다.
`
11. M7 — 배포·운영 검증
`M0에서 선택한 배포 방식 하나를 먼저 완성하라.

LOCAL_DESKTOP인 경우:
- Electron이 백엔드 시작→DB migration→health 확인→UI 로드→안전한 종료를 담당한다.
- DATA_DIR은 설치 경로가 아닌 쓰기 가능한 사용자 데이터 영역의 절대경로다.
- 제안 경로는 UI /app/, 기존 API 루트 경로와 새 /api/v2를 분리한다.
 BrowserRouter basename과 SPA fallback은 /app 범위에서만 처리한다.
- 백엔드는 127.0.0.1로 제한하고, 시작 실패·포트 충돌·경로 문제를 화면에서 설명한다.
- 패키징 런타임에 맞는 better-sqlite3/winax를 검증한다.
 테스트 PC에 Node 또는 한글이 설치되어 있다고 가정하지 않는다.

INSTITUTION_SERVER인 경우:
- UI와 API는 같은 HTTPS origin으로 서비스한다.
- 다른 PC의 localhost:3000을 API 주소로 쓰지 않는다.
- SQLite 파일은 서버 로컬 디스크에 두고 담당자 PC에 공유파일로 배포하지 않는다.
- 기관 보안환경에 맞는 세션 저장소·접속제한·서비스 재기동·백업을 검증한다.

공통:
- 외부 AI OFF, 합성자료 모드, 전송 승인과 실제 전송 파일 확인을 분리한다.
- 민감정보/원문 AI 응답/비밀키를 로그에 남기지 않는다.
- 승인된 근거의 삭제 제한과 백업/복구를 테스트한다.
- QA-042~048 및 해당 배포 모드의 QA-051을 수행한다.

설치 파일 생성 성공과 다른 PC의 실제 사용 검증을 구분해서 보고하라.
`
**외부 근거:** 운영 스키마 변경·Electron 보안·SQLite 일관 백업의 구현 방향은 공식 문서를 참고합니다. 실제 API는 저장소에 설치된 버전과 대조해야 합니다. [T01](https://typeorm.io/docs/migrations/why/) / [T02](https://www.electronjs.org/docs/latest/tutorial/security) / [T03](https://www.sqlite.org/backup.html)

## 12. M8 — 실무 검증과 논문 자료

`구현된 범위에 대해서만 사용자 검증을 설계하라.

- 동일 난이도의 문서 묶음으로 기존 방식과 시스템 방식을 비교한다.
- 원본 처리시간, AI/변환 대기시간, 사람이 검토한 시간, 보정 횟수를 분리한다.
- 익숙해지는 순서 효과와 숙련자/비숙련자 차이를 기록한다.
- 정답지 작성자와 판정 이견 해결 절차를 정한다.
- 누락/불일치/정상/예외/기술실패 표본을 구분한다.
- 추출 정확도, 불일치 검출, 자료 부족의 오승인, 최종결정 이력 보존을 따로 측정한다.
- 사용자 수·문서 수·테스트 기간·실패 사례를 숨기지 않는다.
- 논문 서술은 실제 수행한 실험의 범위로 제한한다.
- 합성자료 결과를 실제 행정 자격검증 성능으로 보고하지 않는다.

실제 결과가 없으면 표의 결과 칸은 '미측정'으로 유지하고 계획만 작성하라.
`
