## 1. 규칙 원장 대표 규칙

규칙은 코드가 아니라 JSON 원장(`apps/server/resources/validation-rules/`)에 있습니다.
지침이 개정되면 코드를 고치지 않고 원장만 교체합니다.

| 원장 파일 | 단계 | 대상 | 규칙 수 |
|---|---|---|---|
| `SENIOR-company.json` | 4단계 기업신청 | COMPANY | 4 (R-101~104) |
| `SENIOR-worker.json` | 5단계 근로자신청 | WORKER | 11 (R-200~210) |
| `SENIOR-subsidy.json` | 6단계 지원금신청 | SUBSIDY | 13 (R-301~309) |
| | | | **28** |

### ① 교차검증 — `crossCheck`

**파일:** `apps/server/resources/validation-rules/SENIOR-company.json` (4단계 기업신청)

서로 다른 세 서류에서 추출된 동일 항목을 대조합니다.

**설계 의도:** 서류 간 교차대조를 AI가 아니라 규칙엔진이 수행합니다.
AI는 각 서류에서 값을 읽는 역할만 하고, 비교·판정은 결정적 코드가 담당합니다(ADR-07).

### ④ 예외처리 — `exceptionRule` (엔진 구현, 규칙 0건)

**구조는 있고 내용은 비어 있습니다.** 이 구분이 이 절의 핵심입니다.

| | 상태 |
|---|---|
| 타입·원장 형식 | 구현 (2026-11-13) |
| 엔진 평가 분기 | 구현 (2026-11-13) |
| 승인 사유 기록 · 예외 후보 집계 | 구현 (2026-11-13) |
| **원장에 등록된 예외 규칙** | **0건** |

비어 있는 이유는 기술적 제약이 아닙니다. **예외 규칙은 지침서에 없고 실무자의 경험에만
있기 때문에**, 내용을 아는 사람이 적어 주기 전에는 만들 수 없습니다. 설계 단계에서 적어 둔
예시(법인전환·계좌압류)는 실제로 겪은 사례가 아니므로 원장에 넣지 않았습니다.

**파일:** `apps/server/src/modules/validation/validation-rules.service.ts`

```typescript
// exceptionRule 전용 — 기본 규칙이 '걸렸을 때'만 평가된다
appliesWhen?: { failedRule: string; verdicts?: RuleVerdict[] }; // 기본 ['NEEDS_REVIEW','FAIL']
conditions?: ExceptionCondition[];
requiresDocument?: DocumentTypeCode;   // 예외 인정에 필요한 추가 서류
onMatch?: RuleVerdict;                 // 기본 NEEDS_REVIEW (자동 통과 금지)
guidance?: string;                     // 담당자 안내 문장
source?: RuleSource;                   // 출처·등록자·등록일 (심사③ 요구사항)
version?: number;                      // 수정 시 +1, 이전 내용은 git 이력으로 보존
```

**파일:** `apps/server/src/modules/validation/domain-validation.engine.ts`

```typescript
/**
 * 기본 결과에 예외 평가를 덧붙인다.
 * - 조건을 만족한 예외는 결과 1건으로 추가(exceptionOf = 기본 규칙 id)
 * - 기본 결과에는 appliedExceptions 로 표시만 하고 verdict 는 그대로 둔다
 */
private applyExceptions(base, exceptionRules, input): RuleResult[] {
  for (const rule of exceptionRules) {
    const target = base.find((r) => r.ruleId === rule.appliesWhen?.failedRule);
    if (!target) continue;
    const verdicts = rule.appliesWhen?.verdicts ?? ['NEEDS_REVIEW', 'FAIL'];
    if (!verdicts.includes(target.verdict)) continue;      // 통과한 규칙은 따지지 않는다
    if (!(rule.conditions ?? []).every((c) => this.matchCondition(c, input, evidence))) continue;

    // PASS 로 내리는 것은 '예외를 증명하는 서류'가 실제로 있을 때만 허용한다
    let verdict = rule.onMatch ?? 'NEEDS_REVIEW';
    if (verdict === 'PASS' && !input[rule.requiresDocument]) verdict = 'NEEDS_REVIEW';

    added.push({ ...,  verdict, exceptionOf: target.ruleId });
    target.appliedExceptions = [...(target.appliedExceptions ?? []), rule.id];  // 판정은 안 바꿈
  }
}
```

**논문에 쓸 만한 지점 세 가지**

1. **예외는 판정을 뒤집지 않습니다.** 기본 규칙의 `verdict`는 그대로 두고 `appliedExceptions`로
   표시만 합니다. 예외에 해당하더라도 "이런 예외로 보이니 무엇을 확인하라"고 안내할 뿐,
   기계가 통과시키지 않습니다 (ADR-07: AI는 추출, 규칙엔진은 대조, 사람은 결정).
2. **`PASS`는 근거서류가 있을 때만.** `onMatch: 'PASS'`로 적어도 `requiresDocument`가 실제로
   제출되지 않았으면 `NEEDS_REVIEW`로 낮추고 필요한 서류명을 메시지에 붙입니다.
   원장 작성자의 실수가 곧바로 자동 통과로 이어지지 않게 하는 안전장치입니다.
3. **원장 오기입이 전체 판정을 깨지 않습니다.** `type`이 맞지 않거나 `appliesWhen.failedRule`이
   같은 원장에 없는 규칙은 **그 규칙만** 경고 로그와 함께 제외됩니다.

**예외 규칙이 기본 규칙 목록에 잘못 들어간 경우**도 조용히 통과시키지 않습니다.

```typescript
case 'exceptionRule':
  // 예외 규칙은 원장의 exceptionRules 에 넣어야 평가된다. 여기로 왔다는 것은 원장 오기입이다.
  return { ..., verdict: 'NEEDS_REVIEW',
           message: '예외 규칙은 원장의 exceptionRules 에 등록해야 평가됩니다(원장 확인 필요).' };
```

"모르는 것을 통과로 집계하지 않는다"(설계서 §10.4)가 코드 수준에서 지켜지고 있음을 보여줍니다.

## 2. 규칙 로딩 코드

**파일:** `apps/server/src/modules/validation/validation-rules.service.ts` (113~150행)

```typescript
/**
 * 검증 규칙 원장 로더. `validation-rules/{typeCode}-{target}.json` 을 읽어 캐시한다.
 * 규칙을 코드에 두지 않고 데이터로 관리(REQ3) — S2(검증규칙 관리)에서 이후 파일만 수정.
 */
@Injectable()
export class ValidationRulesService {
  private readonly logger = new Logger(ValidationRulesService.name);
  /** key = `${typeCode}:${target}` */
  private readonly ledgers = new Map<string, RuleLedger>();

  constructor() {
    this.load();                                  // 서버 기동 시 1회 적재
  }

  private load(): void {
    const dir = path.join(resourcesDir, 'validation-rules');
    let files: string[] = [];
    try {
      files = fs.readdirSync(dir).filter((f) => f.endsWith('.json'));
    } catch (error) {
      this.logger.error(`검증규칙 디렉터리 로드 실패(${dir}): ${error instanceof Error ? error.message : error}`);
      return;                                     // 외부 자원 실패가 서버 기동을 막지 않는다
    }
    for (const file of files) {
      const filePath = path.join(dir, file);
      try {
        const ledger = JSON.parse(fs.readFileSync(filePath, 'utf-8')) as RuleLedger;
        this.ledgers.set(`${ledger.typeCode}:${ledger.target}`, ledger);
      } catch (error) {
        this.logger.error(`검증규칙 파일 로드 실패(${filePath}): ${error instanceof Error ? error.message : error}`);
      }
    }
    this.logger.log(`검증규칙 원장 ${this.ledgers.size}건 로드`);
  }

  getLedger(typeCode: string, target: 'COMPANY' | 'WORKER' | 'SUBSIDY'): RuleLedger | null {
    return this.ledgers.get(`${typeCode}:${target}`) ?? null;
  }
}
```

**실제 기동 로그**

```
[ValidationRulesService] 검증규칙 원장 3건 로드
[JobClassificationService] 직종분류표 495건 로드
```

사업유형(`typeCode`) × 단계(`target`)를 키로 캐시하므로,
**새 사업유형을 추가할 때 JSON 파일만 넣으면 코드 수정이 필요 없습니다.**

규칙 실행 진입점 — **파일:** `apps/server/src/modules/validation/domain-validation.engine.ts` (63~69행)


### 3.5 결과 구조 (타입 정의)

**파일:** `packages/shared/src/types/validation.ts`

```typescript
export type RuleVerdict = 'PASS' | 'NEEDS_REVIEW' | 'FAIL';

export interface RuleResult {
  ruleId: string;
  type: ValidationRuleType;
  label: string;
  verdict: RuleVerdict;
  /** 왜 그렇게 판정했는지 한글 근거 문장 (실무자 검토용, REQ4). */
  message: string;
  /** 비교값·조회결과 등 근거 데이터 (대조 화면 "근거 보기"). */
  evidence?: Record<string, unknown>;
}
```

**모든 판정에 `message`(한글 근거)와 `evidence`(비교값)가 붙습니다.**
설명가능성(explainability) 논거로 쓸 수 있습니다 — 담당자는 "왜 확인필요인지"를
규칙 ID와 실제 대조값으로 확인할 수 있습니다.

## 4. 개인정보 마스킹 코드

**파일:** `apps/server/src/common/masking.util.ts`

```typescript
/**
 * 개인식별정보(주민등록번호) 마스킹 유틸.
 *
 * 보안 안내문이 "외부 AI 전송 전 개인식별정보 마스킹"을 약속하므로 analyze() 경계에서 적용한다.
 * - Gemini로 나가는 텍스트 프롬프트: 마스킹 후 전송
 * - 추출 결과(extractedData): 저장 전에 마스킹 → DB에 평문 주민번호가 남지 않음
 *
 * 주민번호 형식: 6자리-7자리. 뒤 7자리 중 성별 1자리만 남기고 가린다.
 */
const RRN_PATTERN = /(\d{6})[-\s]?([1-4]\d{6})/g;

/** 문자열 안의 주민번호를 `######-G******` 로 마스킹한다. */
export function maskResidentNumbers(text: string): string {
  return text.replace(RRN_PATTERN, (_m, front: string, back: string) => `${front}-${back[0]}******`);
}

/** JSON 값을 재귀 순회하며 문자열의 주민번호를 마스킹한다. 다른 타입은 그대로 둔다. */
export function maskDeep<T>(value: T): T {
  if (typeof value === 'string') return maskResidentNumbers(value) as unknown as T;
  if (Array.isArray(value)) return value.map((v) => maskDeep(v)) as unknown as T;
  if (value && typeof value === 'object') {
    const out: Record<string, unknown> = {};
    for (const [k, v] of Object.entries(value as Record<string, unknown>)) out[k] = maskDeep(v);
    return out as unknown as T;
  }
  return value;
}
```

### 실제 동작 (직접 실행해 확인)

```
입력    신청인 홍길동(750302-1000000) 외 1명 650101-2000000
출력    신청인 홍길동(750302-1******) 외 1명 650101-2******

입력    {"name":"홍길동","residentNumber":"750302-1000000",
         "entries":[{"name":"김철수","rrn":"650101-2000000"}]}
출력    {"name":"홍길동","residentNumber":"750302-1******",
         "entries":[{"name":"김철수","rrn":"650101-2******"}]}

비대상  사업자등록번호 000-00-00000 / 계좌 110-123-456789   ← 변경 없음
```

### 설계 근거

| 결정 | 이유 |
|---|---|
| 성별 자리 `[1-4]`를 패턴에 포함 | 사업자등록번호·계좌번호 오탐 방지 |
| 생년월일 6자리는 남김 | 만 연령 산출(R-200)에 필요 — 가림과 업무 필요의 절충 |
| 뒤 6자리만 가림 | 성별 1자리는 대장 기재 항목이라 유지 |
| `maskDeep`으로 재귀 적용 | 중첩 JSON(배열 속 객체)에 섞인 주민번호까지 처리 |

**적용 지점:** `apps/server/src/modules/documents/documents.service.ts` 의 저장 직전,
`gemini.service.ts` 의 프롬프트 전송 직전 두 곳입니다.

## 5. 예외 후보 집계 결과 (실제 이력)

예외 규칙을 사람이 적어 넣기 전에, **시스템이 먼저 후보를 찾아 줍니다.**
"규칙에 걸렸는데 담당자가 그대로 승인한" 건을 모으면, 지침과 현실이 어긋나는 지점이 드러납니다.

**파일:** `apps/server/src/modules/validation/exception-candidates.ts`

```typescript
/**
 * HUMAN 승인 이력에서 "걸린 채로 승인된 기본 규칙"을 센다.
 *   - source === 'HUMAN' && corrected === true   (담당자가 보고 승인한 시점의 판정)
 *   - 그 시점 결과 중 verdict 가 NEEDS_REVIEW 또는 FAIL 인 규칙
 *   - exceptionOf 가 없는 것만 (예외 규칙 결과 자체는 후보가 아니다)
 * DB·HTTP 를 모르는 순수 함수로 둔다(설계서 F14 — 합성 입력만으로 반복 테스트 가능).
 */
export function deriveExceptionCandidates(histories: JudgmentHistoryLike[]): ExceptionCandidate[]
```

**결과 (2026-11-13, 개발 DB 누적 이력)** — 전문: [samples/exception-candidates-sample.json](samples/exception-candidates-sample.json)

| 규칙 | 대상 | 승인 횟수 | 대상 수 | 최근 승인일 |
|---|---|---|---|---|
| R-203 · 고용보험이력 상실일 < 근로시작일 (이중취득 위험 확인) | 근로자 신청 | **4** | 1 | 2026-11-13 |
| R-104 · 모집직종 참여가능 판정 | 기업 신청 | 1 | 1 | 2026-10-16 |

**논문에 쓸 만한 지점**

같은 규칙(R-203)이 **4번 반복해서 넘어갔습니다.** 한 번이면 담당자의 개별 판단이지만,
반복되면 규칙으로 올릴 후보입니다. 실무자가 "무엇이 예외였는지" 기억을 더듬지 않아도,
**이미 남은 승인 이력에서 후보가 드러난다**는 것이 이 구조의 요지입니다.

다만 **시스템은 후보를 보여줄 뿐 규칙을 만들지 않습니다.** 등록은 사람이 출처를 확인해
`source`(출처·등록자·등록일)와 함께 원장에 적는 단계를 거칩니다.

> 집계값에는 성명·기업명·식별자가 들어가지 않습니다. 승인 사유는 자유 입력이라
> 저장 직전 `sanitizeApprovalReason()`이 주민번호를 마스킹합니다(4장 참조).

## 인용 시 주의

1. **`exceptionRule`은 엔진·원장 형식은 구현되었고 등록된 규칙은 0건**입니다.
   "4유형 전부 구현, 예외 규칙은 실무 사례 수집 후 등록 예정"으로 기술하시고,
   **구현 여부와 데이터 적재 여부를 구분해서** 쓰세요. 0건인 이유(지침에 없고 암묵지)를
   함께 적으면 한계가 아니라 연구 설계로 읽힙니다.
2. **3장 샘플은 가공 입력으로 생성한 결과**입니다. 실제 운영 데이터가 아님을 밝히시되,
   재현 스크립트가 저장소에 있으므로 "재현 가능"은 주장하실 수 있습니다.
3. **5장 예외 후보는 실제 판정 이력에서 나온 값**입니다. 3장 샘플과 성격이 다르므로
   혼동되지 않게 구분해 기술하세요. 승인 사유 1건은 기능 확인 중 입력된 것입니다.
4. **예외처리 축적 구조는 2026-11-13 구현**으로, 11월 1~9일 사용자 평가 **이후**입니다.
