# 근로자 신청 검증 코드 분석

## 전체 흐름

```
문서 분석 완료 (AI 분석)
  └─ autoRegisterWorkerIfNew()         [documents.service.ts]
       ├─ 근로자 DB 자동 등록
       ├─ 형제 서류 workerId backfill
       └─ 다수결 이름 교차검증 보정
  └─ runWorkerValidationIfApplicable()
       └─ validateWorker() 자동 실행

근로자 관리 → "신청 검증" 버튼
  └─ GET /validation/worker/:workerId  [validation.controller.ts]
       └─ validateWorker()             [worker-validation.service.ts]
            ├─ STEP1: 서류 존재 확인
            ├─ STEP2: 대장 매핑값 도출
            └─ STEP3: 규칙 엔진 실행 (R-201~210)
```

---

## 1단계: 근로자 자동 등록 (`autoRegisterWorkerIfNew`)

**파일**: `apps/server/src/modules/documents/documents.service.ts`

### 실행 조건
- 문서 상태 = `ANALYZED`
- 문서 타입 = `WORKER_APPLICATION` (참여신청서)
- `companyId` 존재
- `extractedData.name` 존재

### 처리 순서

```
1. workerId dangling 감지
   └─ workerId가 있는데 Workers 테이블에 없으면 → 초기화 후 진행
      (근로자 삭제 후 재분석 시 발생하는 케이스)

2. 기존 근로자 검색 (동명이인 방지)
   └─ companyId + name + birthDate 조합으로 조회
   └─ 없으면 신규 Worker 레코드 생성

3. WORKER_APPLICATION 문서에 workerId 연결

4. 형제 서류 backfill
   └─ 같은 imapMessageId를 가진 근로자 서류들에 workerId 세팅
   └─ workerId IS NULL 이거나 dangling ID인 서류 모두 포함
      (이 처리가 없으면 검증 시 나머지 서류가 "미제출"로 판정됨)

5. 다수결 이름 교차검증
   └─ 형제 서류들에서 이름 필드 수집
      - name (신청서, 초본, 고용보험 등)
      - workerName (근로계약서)
      - participantName (교육대장)
   └─ 가장 많이 나온 이름으로 Worker.name 보정
      예) 신청서 OCR 오류: 정시원(1표) vs 정세원(4표) → 정세원으로 보정
```

## 2단계: 검증 서비스 (`validateWorker`)

**파일**: `apps/server/src/modules/validation/worker-validation.service.ts`

### STEP 1 — 서류 존재 확인

`SENIOR-2026.json`의 `PARTICIPANT_ELIGIBILITY` 스테이지 기준

| 구분 | 서류 타입 |
|------|----------|
| 필수 (5개) | `WORKER_APPLICATION` 참여신청서 |
|  | `PRIVACY_CONSENT` 개인정보이용동의서 |
|  | `RESIDENT_ABSTRACT` 주민등록초본 |
|  | `EMPLOYMENT_INSURANCE_HISTORY` 고용보험이력 |
|  | `ELIGIBILITY_CONFIRM` 적격확인서 |
| 선택 (2개) | `LABOR_CONTRACT` 표준근로계약서 |
|  | `EDUCATION_LEDGER` 교육대장 |

판정 기준:
- `present`: workerId 기준으로 해당 타입 문서가 존재하는지
- `analyzed`: `extractedData`가 있는지 (AI 분석값 추출됐는지)

### STEP 2 — 대장 매핑값 도출 (`mapLedgerFields`)

| 대장 필드 | 출처 |
|-----------|------|
| 성명 | 초본(우선) → 없으면 신청서 |
| 주민번호(마스킹) | 신청서 `residentNumber` |
| 생년월일 | 주민번호 앞 6자리에서 파생 |
| 성별 | 주민번호 7번째 자리에서 파생 (1·3→남, 2·4→여) |
| 연락처 | 신청서 `phone` |
| 인턴시작일 | 근로계약서 `internStartDate` |
| 인턴종료일 | 근로계약서 `internEndDate` |
| 기업명 | Company DB 조인 |
| 참여유형 | CompanyBusiness DB 조인 |

### STEP 3 — 규칙 엔진 (`SENIOR-worker.json` R-201~210)

**파일**: `apps/server/resources/validation-rules/SENIOR-worker.json`

| 규칙 | 유형 | 내용 | 실패 판정 |
|------|------|------|-----------|
| R-201 | crossCheck | 초본 ↔ 신청서 성명 일치 | NEEDS_REVIEW |
| R-202 | crossCheck | 고용보험이력 ↔ 신청서 성명 일치 | NEEDS_REVIEW |
| R-203 | calcRule | 고용보험 상실일 < 근로시작일 (이중취득 위험) | NEEDS_REVIEW |
| R-204 | calcRule | 근로시작일 기준 90일 이내 참여기업 동일 사업장 근무 여부 | **FAIL** |
| R-205 | calcRule | 인턴약정기간 1~3개월, 수습/인턴 문구 존재 | NEEDS_REVIEW |
| R-206 | riskFlag | 서명·기재 존재 확인 (5개 서류 전체) | NEEDS_REVIEW |
| R-207 | riskFlag | 적격확인서 항목1~5 없음, 항목6 네 패턴 | NEEDS_REVIEW |
| R-208 | calcRule | 교육일자 ≥ 근로시작일 (인턴 시작 이후 교육) | NEEDS_REVIEW |
| R-209 | crossCheck | 성명 일치 (신청서·근로계약서·교육대장, 초본 옵션) | NEEDS_REVIEW |
| R-210 | crossCheck | 근로계약서 기업명 = 선택 기업 일치 | NEEDS_REVIEW |

> 규칙 추가/수정은 `SENIOR-worker.json`만 편집하면 코드 수정 없이 반영됨

### 최종 판정 (`computeStatus`)

```
FAIL 규칙 1개라도 있음      → RISK
필수서류 미제출 or 미분석    → MISSING
NEEDS_REVIEW 규칙 있음      → NEEDS_REVIEW
전부 통과                    → COMPLETE
```

## 3단계: 승인 (`approveWorker`)

**파일**: `apps/server/src/modules/validation/worker-validation.service.ts`

담당자가 대장 매핑값을 수정 후 승인하면:

1. Worker DB 업데이트 (name, birthDate, gender, phone, hireDate, internEndDate)
2. `validateWorker()` 재실행
3. `JudgmentHistory`에 `source: HUMAN`, `corrected: true` 이력 저장
