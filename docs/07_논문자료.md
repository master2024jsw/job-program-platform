## 1. 한 문장으로 말하는 기여

> 행정 서류 검증에서 **LLM의 판단을 신뢰하지 않고**, 추출만 맡긴 뒤 규칙엔진으로 대조하고,
> 기계가 판단을 보류한 건에 대해 **담당자가 무엇을 어디서 고치면 어떻게 되는지까지 지정**하는
> 인간-기계 협업 구조를 설계하고 구현했다.

이게 왜 기여인지 — 비교 대상 두 가지와 다릅니다.

| | AI가 판정까지 함 | 사람이 전부 함 (현행) | **본 연구** |
|---|---|---|---|
| 정확성 책임 | 모델 | 사람 | 규칙엔진(결정적) |
| 틀렸을 때 추적 | 불가 | 기억에 의존 | `ruleId` + 판정이력 |
| 사람의 일 | 결과 확인 | 전부 | 보류된 건만 |
| 개선 측정 | 어려움 | 불가 | AI-사람 일치율 |

## 2. 시스템 구조 — 4층

설계서 ADR-07이 3층(`AI=추출 → 규칙엔진=대조 → 사람=결정`)을 정했고,
본 구현에서 **한 층을 더했습니다.**

```
① AI       = 추출          서류에서 값을 읽는다. 판정하지 않는다.
② 규칙엔진  = 대조          원장(JSON)의 규칙으로 값을 맞춰본다. 결정적.
③ 할일 지정 = 사람에게 넘길 일의 명세   ← 본 연구에서 추가
④ 사람     = 결정          승인하거나, 고쳐서 다시 돌린다.
```

**③이 왜 필요했는가 (논문에 쓸 관찰):**

②까지만 있으면 담당자는 "성명 불일치 — 확인필요"를 받고 *그래서 뭘 해야 하는지*를 스스로
추론해야 합니다. 실제 사용 중 이 지점에서 두 번 막혔습니다.

> "서류를 검토완료로 눌렀는데 기업DB 단계가 안 바뀌어요. 이거 내가 일일히 수정해야 하는거야?"
> "어떤 부분을 체크해서 담당자가 정보를 수정해야 정상적인 루트로 진행되는지가 너무 어려워."

③은 판정을 **행동 문장 세 조각**으로 바꿉니다.

```
무엇이 걸렸나   성명 확인필요 (초본·신청서)          [R-201]
어디서 고치나   근로자 DB 탭 → 수정 → 성명
그러면 무슨 일  맞는 성명으로 고친 뒤 승인하면 근로자 DB 업데이트 예정
```

**핵심 설계 결정:** ③은 AI를 쓰지 않습니다. 규칙 판정에서 **결정적으로** 도출합니다.
같은 판정에는 항상 같은 안내가 나오고, 모델을 교체해도 안내는 흔들리지 않으며, `ruleId`로 역추적됩니다.

구현: [`apps/server/src/modules/validation/next-actions.ts`](../apps/server/src/modules/validation/next-actions.ts)
— DB·HTTP 의존 없는 순수 함수, 단위 테스트 19건.

## 3. 검증 규칙 체계

규칙은 코드가 아니라 **JSON 원장**에 있습니다 (`apps/server/resources/validation-rules/`).
지침이 바뀌면 코드를 고치지 않고 원장을 고칩니다.

| 단계 | 대상 | 규칙 수 | 파일 |
|---|---|---|---|
| 4단계 기업신청 | COMPANY | **4** (R-101~104) | `SENIOR-company.json` |
| 5단계 근로자신청 | WORKER | **11** (R-200~210) | `SENIOR-worker.json` |
| 6단계 지원금신청 | SUBSIDY | **13** (R-301~309) | `SENIOR-subsidy.json` |
| | | **28** | |

규칙 유형은 네 가지입니다.

- `crossCheck` — 여러 서류의 같은 항목을 맞춰본다 (예: 사업자번호 3자 대조)
- `riskFlag` — 한 서류의 필수 기재·서명 존재 확인
- `calcRule` — 계산·날짜 비교 (연령, 인턴기간, 지원금 검산)
- `exceptionRule` — 예외 사유 (미구현)

판정값은 `PASS / NEEDS_REVIEW / FAIL` 세 가지입니다.
(설계서 §10.4는 `INSUFFICIENT_DATA`·`NOT_APPLICABLE`도 제안하나 현재 미구현 — **논문에서는 3값으로 기술할 것**)

### 논문에 넣을 만한 규칙 예시

**R-101 (3자 대조)** — 교차검증을 AI가 아니라 코드가 하는 이유를 보여줍니다.
```json
{"id":"R-101","type":"crossCheck","field":"businessRegistrationNumber",
 "documents":["COMPANY_APPLICATION","BUSINESS_REGISTRATION","WORKPLACE_INSURANCE"],
 "normalize":"brn","onMismatch":"NEEDS_REVIEW"}
```

**R-303 (지원금 검산)** — 신청인이 적어 보낸 금액을 시스템이 다시 계산해 대조합니다.
```
인턴:  min(월급여 × 50%, 400,000원)
채용:  min(월급여 × 50%, 500,000원)
```

## 4. 실제 발견 — 논문의 「문제 분석」에 쓸 사례

실험실 예시가 아니라 **실제 운영 중 발생한 것**이고, 전부 재현·수정·검증까지 했습니다.
논문에서 "LLM 기반 문서 처리의 실패 양상"으로 묶어 쓸 수 있습니다.

### ① 분류는 하고 추출은 멈춘다 (task truncation)

유형을 지정하지 않으면 프롬프트에 해당 서류의 표준 key 목록이 들어가지 않습니다.
모델은 **분류까지만 하고 끝냅니다.**

같은 PDF, 같은 힌트, 유형 지정 여부만 바꾼 통제 실험:

| 조건 | 결과 |
|---|---|
| 유형 지정 O | `{documentType, name:"김영희", residentNumber:"560101-…"}` |
| 유형 지정 X | `{documentType, missingItems:[]}` — **항목 0개** |

→ 근로자 자동등록이 생년월일을 필요로 하므로 **근로자 서류 7종이 전부 DB에 붙지 않음.**

**대응:** 2단계 추출(cascade). 1차가 비었고 종류를 알아냈으면 그 유형으로 한 번 더 호출.
1차에서 값이 나오면 재호출하지 않음(적응형 — 비용은 실패 시에만 증가).

검증: 초본·근로계약서·참여신청서·고용보험이력 **4/4 모두 항목 추출 성공.**

### ② 주석 레이어의 값이 안 보인다 (modality gap)

관공서 서식은 값을 본문이 아니라 PDF **주석(FreeText) 레이어**로 얹는 경우가 있습니다.
사람 눈에는 보이지만 텍스트 추출에도, 모델이 보는 이미지에도 안 잡힙니다.

실제: 4대보험 가입내역 확인서에 사업장명칭·대표자가 또렷이 적혀 있는데
AI가 **"사업장 명칭 및 대표자 성명이 공란으로 기재되어 있습니다"**라고 판정.

**대응:** 분석 전에 주석 글자를 추출해 프롬프트에 함께 전달.
→ `WORKPLACE_INSURANCE`에서 `companyName`·`representativeName` 정상 추출.

### ③ 빈 검토값이 멀쩡한 추출값을 가린다 (state shadowing)

추출이 빈 상태에서 담당자가 「검토완료」를 누르면 빈 `reviewedData`가 저장됩니다.
그 뒤 추출 버그를 고쳐 재분석해도 `reviewedData ?? extractedData` 때문에 계속 빈 값을 읽습니다.
**화면에는 값이 보이는데 DB에는 안 들어오는** 상태가 됩니다.

**대응:** "빈 검토값은 추출값을 가리지 않는다." 담당자가 실제로 입력한 값은 그대로 우선.
단위 테스트 10건으로 고정.

### ④ 스키마에 없으면 묻지도 않는다

근로계약서에 `월(일, 시간)급 : 2,600,000 원`이 적혀 있는데 추출 스키마에 급여 항목이 없어
AI가 임금 조항을 통째로 건너뛰었습니다. 그 결과:

```
급여 미추출 → 근로자 대장 급여 공란 → 지원금 '자료 부족 0원'
            → R-303 산정 검산 불가 → R-306 급여 대조 불가
```

**연쇄 실패**입니다. 하나의 스키마 누락이 네 지점에서 증상으로 나타났습니다.
논문에서 "추출 스키마가 곧 시스템의 관찰 범위를 정한다"는 논지로 쓸 수 있습니다.

덧붙여 같은 수정에서 `payUnit`(월/일/시간)을 함께 받도록 했습니다 —
서식이 "월(일, 시간)급"이라 일급을 적는 기업이 있고, 그걸 월급으로 오인하면 지원금이 과소 산정됩니다.

## 5. 학술적 근거

**⚠ 서지사항은 반드시 원문에서 재확인할 것.**

| 본 연구의 요소 | 대응 개념 | 참고 문헌 |
|---|---|---|
| `NEEDS_REVIEW` = 기계의 판단 보류 | Reject option / 기권 | Chow (1970), *On optimum recognition error and reject tradeoff*, IEEE Trans. Information Theory |
| 기권율과 정확도의 trade-off | Selective classification | Geifman & El-Yaniv (2017), NeurIPS |
| 2단계 추출 (분류 → 유형별 추출) | Task decomposition | Khot et al. (2023), *Decomposed Prompting*; Wei et al. (2022), *Chain-of-Thought Prompting* |
| 1차 성공 시 재호출 생략 | Adaptive model cascade | Chen et al. (2023), *FrugalGPT* |
| 판정 근거 + 정정 위치 제시 | Human-AI Interaction Guidelines G9(효율적 정정), G11(왜 그랬는지 설명) | Amershi et al. (2019), CHI |
| 시스템이 다음 행동을 제안 | Mixed-initiative interface | Horvitz (1999), CHI |
| 담당자 정정을 학습 신호로 축적 | Active learning | Settles (2009), *Active Learning Literature Survey*, UW-Madison TR1648 |
| 모델 신뢰도의 보정 필요성 | Calibration | Guo et al. (2017), *On Calibration of Modern Neural Networks*, ICML |

### 쓸 수 있는 문장 형태 (초안)

> 본 시스템은 LLM의 추출 결과를 직접 신뢰하지 않고, 규칙 원장(R-101~R-309, 총 28개)에 의한
> 결정적 대조를 거쳐 `PASS / NEEDS_REVIEW / FAIL`로 분류한다. `NEEDS_REVIEW`는 기계가 판단을
> 보류하고 사람에게 위임하는 상태로, Chow(1970)가 제시한 기권 옵션(reject option)을 행정 문서
> 검증에 적용한 것이다. 나아가 위임 시 Amershi et al.(2019)의 설계 지침 G9·G11을 반영하여
> 판정 근거와 정정 위치, 정정 후의 결과를 함께 제시함으로써 담당자의 의사결정 비용을 낮춘다.

## 6. 측정 — "점점 고도화된다"를 어떻게 증명하는가

여기가 논문의 **정량 평가** 자리입니다. 장치는 이미 깔려 있고, 데이터만 쌓으면 됩니다.

### 이미 쌓이고 있는 것

`judgment_history` 테이블:

| 컬럼 | 뜻 |
|---|---|
| `target_type` | COMPANY / WORKER / SUBSIDY |
| `status` | 그때의 전체 판정 |
| `result` | 규칙별 판정 전체 (JSON) |
| `source` | **`AI`** = 자동 판정 / **`HUMAN`** = 담당자 승인 |
| `corrected` | 담당자가 값을 고쳤는가 |

같은 `target_id`에 대해 `AI` 판정과 뒤이은 `HUMAN` 판정이 **쌍으로** 남습니다.

### 낼 수 있는 지표

1. **규칙별 AI-사람 일치율** — `R-201은 90%, R-206은 40%` 식으로 나오면
   *어느 규칙이 약한지*가 수치가 됩니다. 다음 고도화 대상이 데이터로 정해집니다.
2. **기권율(abstention rate)** — 전체 중 `NEEDS_REVIEW` 비율.
   낮추되 정확도를 지키는 것이 목표 (Geifman & El-Yaniv의 risk-coverage 곡선).
3. **담당자 처리 시간** — 할일 안내 도입 전후 비교. (측정 장치 미구현)
4. **추출 정확도** — 합성 서류 17종 대 정답지(`sample-case.json`) 항목별 일치율.

### 아직 없는 것 (논문 집필 중 만들어야 함)

- [ ] `npm run ai:score` — 합성 서류 17종을 돌려 정답지와 대조하고 항목별 정확도를 내는 스크립트
- [ ] 판정이력에서 규칙별 일치율을 집계하는 질의
- [ ] 비교 대상(baseline) 정의 — "규칙엔진 없이 AI 판정만" 조건에서 같은 서류를 돌린 결과

> **현재 상태를 정직하게:** 판정이력은 쌓이고 있으나 **표본이 1개 기업·1명 근로자**입니다.
> 지금 수치를 내면 통계적 의미가 없습니다. 논문 집필과 병행해 테스트 건수를 늘리거나,
> 합성 서류로 표본을 만들어야 합니다.

## 8. 한계 — 논문에 먼저 적을 것

심사에서 지적되기 전에 스스로 밝히는 편이 낫습니다.

1. **표본이 작습니다.** 1개 기업, 1명 근로자, 15건 서류. 정량 평가는 아직 못 합니다.
2. **단일 사업 유형에만 적용됐습니다.** 일반형만 구현했고 세대통합형·장기취업유지형은
   정책 원장이 없어 계산하지 않고 사유를 돌려줍니다 (추측하지 않는 것이 설계 결정).
3. **AI 모델에 의존합니다.** Gemini API 호출이 전제이고, 모델 교체 시 추출 정확도가 바뀝니다.
   다만 ③ 할일 지정 층은 결정적이라 영향을 받지 않습니다 — 이 분리가 본 설계의 방어 지점입니다.
4. **판정값이 3개뿐입니다.** 설계서 §10.4의 `INSUFFICIENT_DATA`·`NOT_APPLICABLE`이 미구현이라
   "자료가 없어서 판단 못 함"과 "확인이 필요함"이 같은 `NEEDS_REVIEW`로 묶입니다.
5. **지침 변경 추종은 수동입니다.** 원장이 JSON으로 분리돼 있어 코드 수정은 불필요하지만,
   지침 개정을 사람이 읽고 원장에 옮겨야 합니다.
6. **확정되지 않은 정책 항목이 남아 있습니다.** `SENIOR-2026-GENERAL.json`의 `unspecified` 4건
   (6개월 계속고용 확인 방법, 월급여의 정의, 신청 기한 등). 추측 대신 미해결로 표시해 두었습니다.
